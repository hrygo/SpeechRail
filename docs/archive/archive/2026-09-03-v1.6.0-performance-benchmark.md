# SpeechRail v1.6.0 性能基准与资源监控报告 (Performance Baseline Report)

> **测试版本**：`SpeechRail v1.6.0`（共享权重 realtime 多会话引擎；本次含 stream dispatcher 空闲存活与断开槽释放修复）
> **报告时间**：2026-09-03
> **测试环境**：Apple M5 Max (18 核 CPU / 128GB 统一内存)，macOS 26.6.2，Python 3.12，MLX (MPS)
> **测量工具**：macOS 系统原生 `footprint -f bytes`（采集 `phys_footprint` 物理内存）、`examples/perf/bench_asr.py`、`bench_tts.py`、`bench_realtime.py`、`sample_resources.py`
> **当前状态**：ASR INT8 内存量化；native realtime 使用**专用 streaming worker**（懒启动，首个 realtime 会话才拉起）；TTS 启用 256MB 显存池限额；Diarization (Sortformer) 就绪。
> **验证范围**：v1.6.0 服务经 `/health`、`/readyz`、`/v1/models`（13）、`/v1/voices`（4）全绿；REST smoke（TTS + ASR）+ realtime 并发冒烟（2 会话 + batch 同期）+ 连续 3 会话基准全部通过；修复前复现的 `backend_busy`（第 3 会话）与空转写不再出现。

## 1. 真实物理内存与 CPU 资源基线 (Physical Footprint Baseline)

> **统计口径**：Apple Silicon 统一内存下，MLX/Metal 显存分配计入物理内存池。严格采用 `footprint` 采集 `phys_footprint` 与压测峰值 `phys_footprint_peak`。
> **脚本局限说明**：`sample_resources.py` 通过命令行区分 worker，而 streaming 与 batch worker 共用 `qwen3_worker.py` 模块入口，当前版本会把两者合并计入 `batch-asr`；realtime 会话懒启动，采样窗口无 realtime 会话时 streaming worker 尚未拉起（增量内存未单独拆分）。

| 进程组件 | 运行配置 | 预热常驻物理内存 (Footprint) | 压测峰值物理内存 (Peak) | 峰值 CPU | 运行与显存行为分析 |
|---|---|---|---|---|---|
| **主服务进程 (Host FastAPI)** | `speechrail serve` | **546.8 MB** | **546.8 MB** | 0.7% | 路由、协议解析、ffmpeg 解码与调度 |
| **ASR Worker (batch)** | `qwen3_worker.py` INT8 | **2,536.5 MB (~2.54 GB)** | **9,148.1 MB (~9.15 GB)** | 79.0% | INT8 内存即时量化；压测峰值来自 30s 长音频并发负载 |
| **Qwen3 TTS Worker** | `qwen3_tts_worker.py` | **4,941.5 MB (~4.94 GB)** | **5,314.8 MB (~5.31 GB)** | 1.4% | VoiceDesign 1.7B bf16，256MB 缓存池上限 |
| **全系统总物理常驻 (Total)** | -- | **8,024.8 MB (~8.02 GB)** | **15,009.7 MB (~15.01 GB)** | -- | 峰值后回落正常，无泄漏滞留 |

> 与 v1.5.2（batch 2,542.7 MB / 总常驻 8,022.9 MB）相比，v1.6.0 常驻持平（batch 2,536.5 MB / 总常驻 8,024.8 MB）；本次采样窗口无 realtime 会话，streaming worker 未计入。

## 2. 非流式 ASR 延迟与 RTF 实测基线 (`POST /v1/audio/transcriptions`)

> **测试配置**：`model=speechrail/qwen3-asr-1.7b`, `response_format=json`, 重复 $N=3$ 取均值。16kHz 单声道 PCM16 中文语音样本。

| 音频时长 (Duration) | 平均处理耗时 (Mean Latency) | 实时率 (RTF) | 最小 / 最大耗时 | 转写文本 |
|---|---|---|---|---|
| **2.8 秒** (短音频) | **0.13 s** | **0.05x** | 0.11s / 0.16s | “你好，这是本地语音识别与合成。” |
| **8.6 秒** (中音频) | **0.23 s** | **0.03x** | 0.22s / 0.23s | “你好，这是本地语音识别与合成服务的性能基准测试…” |
| **15.5 秒** (长音频) | **0.40 s** | **0.03x** | 0.40s / 0.41s | 长语音连续转写，吐字对齐清晰 |
| **32.0 秒** (超长音频) | **0.82 s** | **0.03x** | 0.79s / 0.87s | 长音频吞吐极稳（比播放快 ~39 倍） |

### 并发吞吐实测 (4 Workers, N=8)
- **并发参数**：4 线程并发压测 8.6s 音频切片，共 8 次请求
- **吞吐表现**：Wall time = **1.84s**，成功率 = **8/8 (100%)**
- **平均延迟**：**0.75s** (P95 = **0.90s**)
- **系统吞吐量**：**4.35 req/s**（等效总体实时率 $RTF_{total} = \mathbf{0.03x}$）

## 4. 双向流式 WebSocket 实测基线 (`WS /v1/realtime`)

> **测试配置**：标准 OpenAI Realtime 协议，8.6s PCM16 语音流，3 轮**连续**会话测试。v1.6.0 关键回归：会话 3 不再出现 `backend_busy`（修复前因断开/取消泄漏 factory 槽位，累计 2 个泄漏会话后所有新会话被拒）；空闲静默不再误判 worker 故障（修复前共享 dispatcher 空闲 120s 后永久退出，新会话 `connect()` 挂起至超时）。

| 测试项 | Session 1 (冷启动) | Session 2 (稳定) | Session 3 (稳定) | 指标说明 |

## 5. 性能与资源健康结论

1. **显存治理健康度**：ASR batch 常驻 **2.54 GB**、TTS **4.94 GB**、主进程 **547 MB**，总常驻 **~8.02 GB**；峰值 **~15.01 GB** 后正常回落，无泄漏滞留。
2. **延迟与吞吐能力**：
   - 非流式 ASR 32s 音频转写仅需 **0.82s**（RTF 0.03x~0.05x）；
   - 并发 4 线程吞吐 **4.35 req/s**（P95 0.90s）；
   - 流式 TTS 首包延迟稳定 **44ms**；
   - **Realtime 三连会话 100% 成功**——v1.6.0 修复的 dispatcher 空闲误判与断开槽泄漏在连续会话场景下均未复现。
3. **服务状态**：ASR、TTS、Realtime、Diarization 全能力就绪（`readyz=200`），全流程无异常退出。

## 6. 与 v1.5.2 基线对比摘要

| 指标 | v1.5.2 | v1.6.0 | 变化 |
|---|---|---|---|
| 非流式 ASR 3s (RTF) | 0.13s / 0.05x | 0.13s / 0.05x | 持平 |
| 非流式 ASR 8s (RTF) | 0.25s / 0.03x | 0.23s / 0.03x | 微提升 |
| 非流式 ASR 32s (RTF) | 0.86s / 0.03x | 0.82s / 0.03x | 微提升（~39x） |
| 并发吞吐 (4w×8) | 4.00 req/s (P95 1.00s) | 4.35 req/s (P95 0.90s) | +9% |
| TTS 短句 / 长句 (RTF) | 1.29s / 0.37x、3.10s / 0.36x | 1.12s / 0.34x、2.74s / 0.33x | 提升 |
| Realtime ASR commit | 2707/2616/2574ms (0.30x) | 2284/2284/2288ms (0.26x) | 提升 |
| Realtime TTS TTFA | 74~78ms | 44ms | 提升 |
| 总常驻内存 | 8,022.9 MB | 8,024.8 MB | 持平 |

> **说明**：v1.6.0 数字与 v1.5.2 同口径实测（同机、同 fixtures、同一 `bench_*`/`sample_resources` 工具链）；ASR/TTS 的微提升在测量噪声范围内，核心改善在 realtime 稳定性维度。样本内 realtime 三连会话与并发冒烟（2 会话 + batch 同期）均无 `backend_busy`/空转写/死锁。
