# SpeechRail v1.5.2 性能基准与资源监控报告 (Performance Baseline Report)

> **测试版本**：`SpeechRail v1.5.2`（缺陷修复版：realtime 槽位释放、断开即释放、活跃会话免回收、transport 读写锁分离）
> **报告时间**：2026-09-03
> **测试环境**：Apple M5 Max (18 核 CPU / 128GB 统一内存)，macOS 26.6.2，Python 3.12，MLX (MPS)
> **测量工具**：macOS 系统原生 `footprint -f bytes`（采集 `phys_footprint` 物理内存）、`examples/perf/bench_asr.py`、`bench_tts.py`、`bench_realtime.py`、`sample_resources.py`
> **当前状态**：ASR INT8 内存量化；native realtime 使用**专用 streaming worker**（懒启动，首个 realtime 会话才拉起）；TTS 启用 256MB 显存池限额；Diarization (Sortformer) 就绪。
> **验证范围**：v1.5.2 服务经 `/health`、`/readyz`、`/v1/models`（13）、`/v1/voices`（4）全绿；叠加冒烟（batch×5 + realtime 并发）与串行双会话冒烟均通过，无 `backend_busy`/`worker_not_started`/死锁。

## 1. 真实物理内存与 CPU 资源基线 (Physical Footprint Baseline)

> **统计口径**：Apple Silicon 统一内存下，MLX/Metal 显存分配计入物理内存池。严格采用 `footprint` 采集 `phys_footprint` 与压测峰值 `phys_footprint_peak`。
> **脚本局限说明**：`sample_resources.py` 通过命令行区分 worker，而 streaming 与 batch worker 共用 `qwen3_worker.py` 模块入口，当前版本会把两者合并计入 `batch-asr`；realtime 会话首次连接才启动 streaming worker（增量内存未单独拆分）。

| 进程组件 | 运行配置 | 预热常驻物理内存 (Footprint) | 压测峰值物理内存 (Peak) | 峰值 CPU | 运行与显存行为分析 |
|---|---|---|---|---|---|
| **主服务进程 (Host FastAPI)** | `speechrail serve` | **539.1 MB** | **539.1 MB** | 0.6% | 路由、协议解析、ffmpeg 解码与调度 |
| **ASR Worker (batch)** | `qwen3_worker.py` INT8 | **2,542.7 MB (~2.54 GB)** | **9,159.8 MB (~9.16 GB)** | 77.6% | INT8 内存即时量化；压测峰值来自 30s 长音频并发负载 |
| **Qwen3 TTS Worker** | `qwen3_tts_worker.py` | **4,941.0 MB (~4.94 GB)** | **5,313.8 MB (~5.31 GB)** | 1.1% | VoiceDesign 1.7B bf16，256MB 缓存池上限 |
| **全系统总物理常驻 (Total)** | -- | **8,022.9 MB (~8.02 GB)** | **15,012.7 MB (~15.01 GB)** | -- | 峰值后回落正常，无泄漏滞留 |

> 与 v1.5.0（统一 ASR worker 7.85 GB 常驻）相比，v1.5.2 因 dedicated realtime streaming worker 的存在，常驻抬升约 170 MB；这是用独立进程换 batch/realtime 管道隔离的必要代价。

## 5. 性能与资源健康结论

1. **显存治理健康度**：ASR batch 常驻 **2.54 GB**、TTS **4.94 GB**、主进程 **539 MB**，总常驻 **~8.02 GB**；峰值 **~15.01 GB** 后正常回落，无泄漏滞留。
2. **延迟与吞吐能力**：
   - 非流式 ASR 32s 音频转写仅需 **0.86s**（RTF 0.03x~0.05x）；
   - 并发 4 线程吞吐 **4.00 req/s**；
   - 流式 TTS 首包延迟稳定 **73ms ~ 78ms**；
   - **Realtime 三连会话 100% 成功**——v1.5.2 修复的槽位泄漏/断开释放/worker 误回收/读写锁死锁四项缺陷在连续会话与 batch 叠加场景下均未复现。
3. **服务状态**：ASR、TTS、Realtime、Diarization 全能力就绪（`readyz=200`），全流程无异常退出。

## 6. 与 v1.5.0 基线对比摘要

| 指标 | v1.5.0 | v1.5.2 | 变化 |
|---|---|---|---|
| 非流式 ASR 3s (RTF) | 0.10x | 0.05x | 提升 |
| 非流式 ASR 8s (RTF) | 0.03x | 0.03x | 持平 |
| 非流式 ASR 32s (RTF) | 0.02x | 0.03x | 持平 (~快 37x) |
| 并发吞吐 (4w×8) | 3.52 req/s | 4.00 req/s | +14% |
| TTS 短句 / 长句 (RTF) | 0.33x / 0.32x | 0.37x / 0.36x | 持平（时长设定差异） |
| Realtime ASR commit | 365~381ms (0.5x 快) | 2.6s@8.6s 音频 (0.30x) | 见下注 |
| Realtime TTS TTFA | 38~43ms | 73~78ms | 见下注 |
| 总常驻内存 | 7.85 GB | 8.02 GB | +170 MB（dedicated streaming worker） |
| 连续会话稳定性 | 基线不足（v1.5.1 曾泄漏槽位） | 3/3 成功 | **修复后无回归** |

> **Realtime commit/TTFA 对比注**：v1.5.0 报告测的是 8.1s 音频的**窗口化增量** commit（RTF 0.05x），v1.5.2 本次按 skill 标准流程对 **8.6s 整段音频一次 commit**（RTF 0.30x）。两者提交语义不同，不可直接比绝对值；同一提交语义下的稳定性（3 连会话全过）才是 v1.5.2 的核心改善。
