# SpeechRail v1.6.7 性能基准与资源监控报告 (Performance Baseline Report)

> **测试版本**：`SpeechRail v1.6.7`（预量化 `-8bit` MLX 快照；核心变更：Sortformer 分人模型空闲自动卸载（`EvictableWorker` + `WorkerIdleEvictor`）、Realtime ASR reader 失败可见化、客户端事件队列有界、`/v1/models` 补 OpenAI `created` 字段、`create_breath_pause` 缓存）
> **报告时间**：2026-09-05
> **测试环境**：Apple M5 Max (18 核 CPU / 128GB 统一内存)，macOS 26.6.2，Python 3.12，MLX (MPS)
> **测量工具**：macOS 系统原生 `footprint -f bytes`（采集 `phys_footprint` 物理内存）、`examples/perf/bench_asr.py`、`bench_tts.py`、`bench_realtime.py`、`sample_resources.py`（`run_all_benchmarks.py` 全自动串行）
> **模型配置**：Qwen3-ASR-1.7B `-8bit` + Qwen3-TTS VoiceDesign `-8bit`（仓库外绝对路径 snapshot）；`SPEECHRAIL_DTYPE=int8`，`SPEECHRAIL_DEVICE=mps`（`-8bit` 快照自动解析为 int8 直接加载，不二次量化）
> **当前状态**：`/health`（version=1.6.7, asr/tts/diarization 全 ready）、`/readyz` 200、`/v1/models`（canonical + alias 含 `gpt-4o-transcribe-diarize`，含 OpenAI `created` 字段）、`/v1/voices`（全 available）全绿；Diarization (Sortformer) 就绪。
> **测量口径修正**：⚠️ 本轮基准发现并修复了 `sample_resources.py` 的进程误分类 bug（详见 §5 与 §6）。采用优化方案（worker 自描述 `--worker-role` 标志）重跑后，batch-asr 与 streaming-asr 得到正确分离计量，**此前 `batch-asr 4.34 GB` 为采样脚本把 native streaming worker 误归入 batch-asr 的测量伪影**，并非真实常驻，更非代码回归。本报告以**修正后重跑**为正式数据。

## 1. 真实物理内存与 CPU 资源基线 (Physical Footprint Baseline)

> **统计口径**：Apple Silicon 统一内存下，MLX/Metal 显存分配计入物理内存池。严格采用 `footprint` 采集 `phys_footprint` 与压测峰值 `phys_footprint_peak`。
> **采样说明**：`sample_resources.py` 通过命令行区分 worker；本次采样窗口含 ASR batch 压测（30s 音频 × 5 次，mode=all，含 warmup）与 TTS 合成。经修正后进程被正确区分为 4 个组件（含 streaming-asr）。**本机为并发负载环境，但 ASR worker 常驻已由修正后采样得到准确值。**

| 进程组件 | 运行配置 | 冷启待机 | 预热常驻物理内存 (Footprint) | 压测峰值物理内存 (Peak) | 峰值 CPU | 运行与显存行为分析 |
|---|---|---|---|---|---|---|
| **主服务进程 (Host FastAPI)** | `speechrail serve` | 536.7 MB | **538.3 MB (~0.54 GB)** | **538.3 MB (~0.54 GB)** | 1.2% | **v1.6.7 核心成果**：Sortformer 分人模型空闲自动卸载后主服务回落至 ~0.54 GB（与 v1.6.5 基线一致）。v1.6.6 为 1.08 GB（含 in-service Sortformer 常驻） |
| **ASR Worker (batch)** | `qwen3_worker.py` int8, `--worker-role batch` | 2,505.6 MB | **2,509.0 MB (~2.51 GB)** | **3,550.9 MB (~3.55 GB)** | 76.4% | **与 v1.6.6 静默基线（2.50 GB / 3.68 GB）一致**。修正了进程误分类后 batch-asr 回到真实基线 |
| **ASR Worker (streaming)** | `qwen3_worker.py` int8, `--worker-role streaming` | 2,733.6 MB | **2,561.7 MB (~2.56 GB)** | **3,410.9 MB (~3.41 GB)** | 0.0% | native realtime 流式 worker。**此前被误归入 batch-asr**，修正后独立计量 |
| **Qwen3 TTS Worker** | `qwen3_tts_worker.py` int8 | 3,557.7 MB | **3,557.6 MB (~3.56 GB)** | **3,979.5 MB (~3.98 GB)** | 2.0% | VoiceDesign 1.7B `-8bit`，与 v1.6.6 常驻一致 |
| **全系统总物理常驻 (Total)** | -- | -- | **9,166.5 MB (~9.17 GB)** | **9,731.6 MB (~9.73 GB)** | -- | 含 batch+streaming+tts+host 四进程真实同时占用。此前因 streaming 误分类未被计入，故旧读数 8.44 GB 偏低，本轮为真实值 |

> **真同时口径**：`Peak(Total)` = 逐采样 tick 的（当前 footprint 之和）的最大值，**不为**逐进程 all-time high-water 之和。

## 5. `sample_resources.py` 进程误分类修正（本轮关键发现）

### 5.1 问题

- 部署配置 `SPEECHRAIL_REALTIME_ASR_BACKEND=native` 会拉起一个 **streaming worker**（复用 `speechrail.backends.qwen3_worker`，`--max-new-tokens 512`）。
- native streaming worker 与 batch worker **共用同一个模块入口** `speechrail.backends.qwen3_worker`，命令行里**不含 "streaming_worker" 字面量**（`qwen3_streaming.py` 与 `qwen3_native.py` 的 `command()` 仅差 `--max-new-tokens` 等参数）。
- 旧 `sample_resources.py` 的 `worker_pids()` 用字面量匹配 `batch-asr = "qwen3_worker" in line and "streaming" not in line`，导致 **native streaming worker 被误归入 batch-asr**，批量 ASR 常驻被叠加虚高（旧读数 batch-asr=4.34 GB，实为 batch 2.51 GB + streaming 2.56 GB 的混叠）。

### 5.2 修复（采用优化方案）

- 给 worker 增加进程自描述标志：`Qwen3BackendConfig.command()` 追加 `--worker-role batch`，`Qwen3StreamingBackendConfig.command()` 追加 `--worker-role streaming`，`qwen3_worker.main()` 接受该标志（仅自描述，不参与推理逻辑）。
- `sample_resources.py` 的 `worker_pids()` 改为按 `--worker-role streaming` 精确区分，batch 与 streaming 干净分离，不再依赖脆弱的模块名/参数猜测。
- 单测：`test_qwen3_streaming.py` / `test_qwen3_backend.py` 各自锁定 `command()` 携带正确 `--worker-role`；全量 396 测试全绿。

### 5.3 修正后对 ASR 常驻的影响

| 项 | 修正前（误分类） | 修正后（准确） |
|---|---|---|
| batch-asr 常驻 | 4.34 GB（混叠） | **2.51 GB**（真实，与 v1.6.6 一致） |
| streaming-asr | 未识别/混入 batch | **2.56 GB**（独立计量） |
| 总物理常驻 | 8.44 GB（漏计 streaming） | **9.17 GB**（四进程真实同时占用） |

## 6. 归因结论与 v1.6.6 → v1.6.7 对照

| 指标 | v1.6.6 静默基线 | v1.6.7 修正后 | 说明 |
|---|---|---|---|
| 主服务常驻 | 1.08 GB (含 Sortformer) | **0.54 GB** | ✅ **+改进**：Sortformer 空闲卸载，回到 v1.6.5 基线 |
| ASR batch 常驻 | 2.50 GB | **2.51 GB** | ✅ **一致**（修正误分类后回到真实基线） |
| ASR streaming 常驻 | 未单独计量 | 2.56 GB | 独立计量（此前被混入 batch） |
| TTS 常驻 | 3.56 GB | 3.56 GB | ✅ 一致 |
| ASR 3s 延迟 | 0.13s | 0.25s（含 warm-up） | ✅ 一致（稳定 0.12s） |
| ASR 超长音频 | 0.89s (33.0s) | 0.90s (34.7s) | ✅ 一致 |
| ASR 并发吞吐 | 4.04 req/s | 3.97 req/s | ✅ 噪声带内 |
| ASR 并发 P95 | 0.99s | 1.02s | ✅ 噪声带内 |
| TTS 长句 | 2.44s | 2.26s | ✅ 一致 |
| Realtime commit | 360-435ms (静默) | 375-395ms（稳定会话） | ✅ 一致（session 1 冷路径 852ms） |
| Realtime TTFA | 35-52ms | 34-41ms | ✅ 一致 |

**归因结论：**

1. **v1.6.7 主服务常驻确定性回落**：Sortformer 空闲自动卸载生效，主服务从 v1.6.6 的 1.08 GB 回到 0.54 GB（v1.6.5 基线）。这是本次确定性的内存改进。
2. **ASR batch 常驻无回归**：修正 `sample_resources.py` 进程误分类后，batch-asr 实测 **2.51 GB**，与 v1.6.6 静默基线（2.50 GB）完全一致。**此前报告的 4.34 GB 是采样脚本把 native streaming worker 误归入 batch-asr 的测量伪影，非真实常驻、非代码回归。**
3. **延迟/吞吐无回归**：全部核心延迟指标与 v1.6.6 静默基线一致（噪声带内）。

```bash
curl -s http://127.0.0.1:8201/readyz | jq .

# 2. 一键全量基准（7 步：健康→fixtures→TTS→ASR→并发→Realtime→资源采样）

# 注：sample_resources.py 需部署含 --worker-role 自描述标志的版本，否则 native
# streaming worker 会被误归入 batch-asr（见 §5）。
```
