# SpeechRail v1.6.5 稳定性探测报告 (Stability Probe Report)

> **测试版本**：`SpeechRail v1.6.5`（预量化 `-8bit` MLX 快照，`-8bit` 自动解析为 int8 直接加载；`SPEECHRAIL_DTYPE=float16` 仅作用于非预量化快照）
> **报告时间**：2026-09-04
> **测试环境**：Apple M5 Max (18 核 CPU / 128GB 统一内存)，macOS 26.6.2，Python 3.12，MLX (MPS)
> **部署形态**：launchd `com.speechrail` 常驻服务（wheel 安装版），`127.0.0.1:8201` loopback，`.env` 已配置 API key（`/v1` 需鉴权）
> **测量工具**：macOS 原生 `footprint -f bytes`（采集 `phys_footprint` 物理内存）、`examples/perf/bench_asr.py`、`bench_tts.py`、`sample_resources.py`、`concurrent_realtime_smoke.py`
> **模型配置**：Qwen3-ASR-1.7B `-8bit` + Qwen3-TTS VoiceDesign `-8bit`（仓库外绝对路径 snapshot）；`SPEECHRAIL_REALTIME_ASR_BACKEND=native`，`SPEECHRAIL_REALTIME_MAX_SESSIONS` 走默认（3）
> **探测性质**：稳定性验证（并发/背压/会话复用边界/内存泄漏/错误处理/负载后恢复），**非**全量性能基准；使用真实模型推理，非 fake backend
> **结论**：服务在真实模型下并发、背压、实时会话复用、错误拒绝与资源回收全部稳定，与 v1.6.5 性能基线一致，无内存泄漏、无 500、无崩溃。**可信赖。**

---

## 1. 探测范围与方法

本次为稳定性探测，聚焦服务在持续/高并发负载下能否保持稳定、可恢复、无泄漏、无协议违约，而非重跑完整性能曲线。

- 所有推理端点经真实模型 smoke，端点需 `Authorization: Bearer <key>`。
- 并发与负载在真实 MPS worker 上执行；背压探针用临时 auth 感知副本（未改仓库 `probe_queue.py`）。
- 足迹口径：Apple Silicon 统一内存下，MLX/Metal 显存计入物理内存池，严格采用 `footprint` 采集 `phys_footprint` 与进程生命周期峰值 `phys_footprint_peak`。
- 标注约定：**实测**（本次工具测得）、**文档规定**（`contracts/` 与 AGENTS 所述）、**推断**（基于实测的合理推导）。

> 注：`/tmp/audio_30s.wav` 为本地 TTS 合成样本，`ffprobe` 实测时长 **15.76s**（非 30s 标称），运行时按实测时长计。

## 2. 并发与吞吐稳定性（实测）

| 探测项 | 参数 | 结果 |
|---|---|---|
| 核心负载 + 资源采样 | `sample_resources.py --mode batch`，30s(实测15.76s) 音频 × 8，含 warmup | 8 次全部处理成功，无 500、无超时 |
| batch-asr 内存 | 预热常驻 2560.6 MB | 压测峰值 **3492.7 MB**（= 进程生命周期 high-water，未超越） |
| host-fastapi 内存 | 540.2 MB | 峰值 540.7 MB，稳定 |
| 真同时总峰值 | host + batch-asr 同 tick 之和 | **3101.3 MB**（实测口径，非逐进程峰值相加） |
| 并发吞吐 | `bench_asr.py --workers 4 --n 8`（10s 音频） | **ok=8/8**，wall 1.92s，mean **0.78s**，P95 **0.93s**，吞吐 **4.17 req/s**，RTF 0.03x |

**与 v1.6.5 基线对比（推断/实测一致）**：基线报告为 8/8、mean 0.78s、P95 0.94s、4.19 req/s；本次 8/8、0.78s、0.93s、4.17 req/s，**逐项吻合**，说明并发处理与吞吐在一致水平，无退化。

## 3. 背压/队列行为（实测）

`probe_queue`（auth 感知）24 并发上传 10s 音频：

| 结果 | 数 | 说明 |
|---|---|---|
| `200` 成功 | **8** | 恰好达到 admission queue 上限（`SPEECHRAIL_MAX_QUEUE_SIZE` 默认 8），全部转写成功，mean 1.13s，max 1.96s |
| `429 queue_full` | **16** | 超出上限的请求被拒绝，逐一携带 **`Retry-After: 1`** |
| 其他（500/协议错误） | 0 | 无 |

**判定**：背压符合**文档规定** —— 队列/Resource Governor 将并发上限定为 8，超限请求返回稳定 `queue_full` 429 并给出 `Retry-After`，而非无界排队或进程崩溃。被拒绝后重试即可恢复。

## 4. Realtime 会话复用与边界（实测）

`concurrent_realtime_smoke.py /tmp/audio_10s_16k.pcm --sessions 3`（`MAX_SESSIONS` 默认 3）：

- **3 个并发会话全部成功**，共享单个 streaming worker；会话 id 互异（`realtime_*`），无帧错位。
- 三会话转写文本一致（同源 PCM），存在 windowed 增量提交的词级断句特征（如“性能基。准测试”），属**文档规定**的正常 windowed 行为，非错误。
- **批量转写与 3 个实时会话并存**：`POST /v1/audio/transcriptions` 返回 **HTTP 200**，说明 Direction-1 复用下 batch 不受实时会话阻塞。

**边界探测（实测）**：手动占用 3 个会话（session.update + append）后，第 4 个会话 `session.create` 仍成功，但**首次 `input_audio_buffer.append` 返回错误事件 `error.code=backend_busy`**。此行为与**文档规定**一致：`session.create` 在网关层不拦截，达到并发上限时新会话的 append 返回 `backend_busy`（session 保持可用），而非崩溃/挂起。

## 5. TTS 稳定性（实测）

| 句长 | n | 结果 | 稳态区间 | RTF |
|---|---|---|---|---|
| 短句 (20 字) | 5 | 5/5 有效音频 (3.60-3.84s) | run1 6.46s（首词热载），run2-5 **1.01-1.17s** | 稳态 ~0.30x（mean 0.58x 被 warmup 抬高） |
| 长句 (50 字) | 5 | 5/5 有效音频 (8.64-9.52s) | run1-5 全部 **2.40-2.67s** | 0.28x |

**判定**：TTS worker 懒启动后首句 kernel 编译成本（6.46s）在可接受范围，稳态短/长句延迟与 v1.6.5 基线（短 ~0.78-0.97s、长 2.27s / RTF 0.27x）一致，无失败、无异常输出。

## 6. 错误处理边界（实测，fail-closed）

| 输入 | HTTP | error.code | 说明 |
|---|---|---|---|
| corrupt.wav（随机字节） | 422 | `audio_decode_failed` | 含 request_id（`req_9b4a1d25`） |
| empty.wav（空文件） | 422 | `empty_audio` | 稳定 envelope |
| note.txt（text/plain） | 422 | `unsupported_audio_type` | MIME/内容校验 |
| garbage.wav（RIFF 头 + 噪声） | 422 | `audio_decode_failed` | ffmpeg 内容校验判定为不可解码 |
| 缺 file 字段 | 422 | `validation_error` | 请求校验失败 |

**判定**：所有非法输入被拒绝为 **4xx**（统一 error envelope：`error.code`/`error.type`），无 500、无崩溃；服务在坏输入下保持 fail-closed，符合**文档规定**的稳定错误语义。

## 7. 内存泄漏/滞留检测（实测）

| 进程 | 负载前常驻 | 负载后常驻 | 进程峰值 | 判定 |
|---|---|---|---|---|
| host-fastapi | 540 MB | 552 MB | 552 MB | +12 MB，请求处理瞬态，无泄漏 |
| batch-ASR | 2560 MB | 2562 MB | 3492 MB | 无增长 |
| TTS worker | 未运行（懒启动） | 3408 MB | 3977 MB | 与基线 3556 MB 常驻 / 3978 MB 峰值吻合 |

**判定**：经历 8×30s ASR + 并发吞吐 + 24 并发背压 + 3 实时会话 + 2×5 TTS + 多组坏请求后，各 worker 常驻内存回落至基线水平，`phys_footprint_peak` 均未超进程生命周期 high-water，**无泄漏滞留**。

## 9. 结论

服务（v1.6.5，`-8bit` int8/MPS）在本轮稳定性探测中表现稳定：

- **并发**：4 并发 8 请求 100% 成功，吞吐与延迟与基线一致。
- **背压**：队列上限正确，超限返回 `429 queue_full` + `Retry-After`，无无界排队。
- **Realtime**：3 并发会话复用正常、batch 并存不阻塞；达到 `MAX_SESSIONS` 上限后新会话 append 按契约返回 `backend_busy`。
- **内存**：负载后各 worker 回落至基线，无泄漏/滞留。
- **错误处理**：坏输入统一 4xx envelope，fail-closed，无 500。
- **恢复**：压测后 `/health`/`/readyz`/`/v1/models`/`/v1/voices` 全绿。

**未验证/风险（推断）**：
1. 本次为稳定性核心项，**未**重跑完整性能基准（阶梯 RTF/TTFA 全曲线 / `run_all_benchmarks.py`）。
2. `413 audio_too_large`（需 >512MB 上传）与 `400 audio_too_long`（需 >3600s）因构造成本未实测，仅确认配置边界存在。
3. 数小时级长时运行的内存曲线未覆盖，本次为分钟级重复负载。
4. 本报告为归档追溯材料，不构成当前行为或性能承诺；正式性能基准以对应 `*-performance-benchmark.md` 为准。
