## 测量身份与可比性

- 当前 manifest SHA-256 前缀为 `cfdfbefc`，包含 36 个固定 fixture：ASR 3.12/9.36/16.88/37.04s 各 6 次，TTS short/long 各 6 次；ASR fixture digest 前缀沿用 `5ab6f44c`、`4075ad`、`5cde37`、`03cb627`，Realtime 使用固定 16 kHz mono PCM16 fixture。
- 每个 profile 的 `-cold` 行发生在 profile apply 的公共 smoke 之后；因此本轮不把它们宣称为严格 cold，正式分位数只使用 `w01`–`w05` 的 warm N=5。冷态 gate 为 `cold_unavailable`，避免把前置 smoke 后的首次请求误报成冷启动。
- HTTP 通过 `bench_profiles.py` 运行，Realtime 通过 `bench_realtime.py`，并在 session 外围以 `ProcessResourceMonitor` 采样 host、batch 或 streaming worker。RTF 使用 ffprobe/返回 PCM 实测时长，不使用 fixture 名称推断。
- 资源峰值使用完整同 tick 的 PID+start-time 集合求和；HTTP/Realtime 采样窗口均无缺样且 `sampling_complete=true`。HTTP samples 为 quality/balanced/light 的 104/89/84，Realtime samples 为 7/8/7。
- 三档实际身份均通过 `/health`、`/readyz`、`/v1/models`、`/v1/voices` 复核：`quality` 为 `asr-1.7b-q8` + `tts-1.7b-design-q8` VoiceDesign；`balanced` 为 `asr-1.7b-q8` + `tts-0.6b-custom-q8` CustomVoice；`light` 为 `asr-0.6b-q8` + `tts-0.6b-custom-q8` CustomVoice；量化均为 8-bit MLX。
- 与 v1.13.0 共用机器和 ASR/Realtime 输入，但历史报告的 runner、profile 重启/预热时机、TTS 输出长度和资源窗口不完全一致；与 v2.0.2 的 manifest/schema/fixture 一致，但 v2.0.2 仍是不同运行轮次。因此纵向数字只作方向性观察，不设置临时回归阈值。

## 纵向：v2.0.2 历史差异的复现与根因分析

| profile | ASR 9.36s warm p50 RTF：v2.0.2 → v2.0.3 | TTS short warm p50 RTF：v2.0.2 → v2.0.3 | HTTP peak：v2.0.2 → v2.0.3 |
|---|---:|---:|---:|
| quality | 0.0288 → 0.0239（-16.9%） | 0.3147 → 0.2572（-18.3%） | 6765.4 → 6779.1 MB（+0.2%） |
| balanced | 0.0357 → 0.0240（-32.9%） | 0.3908 → 0.2302（-41.1%） | 5878.3 → 5919.6 MB（+0.7%） |
| light | 0.0232 → 0.0154（-33.4%） | 0.3178 → 0.2289（-28.0%） | 4050.7 → 4450.9 MB（+9.9%） |

已确认的因果边界：

1. `2e2920e` 相对上一份 v2.0.2 报告没有修改 `src/speechrail/backends`、`src/speechrail/application` 或 `src/speechrail/runtime`；本 patch 的主要运行时变化是 CLI 将 managed 状态操作统一委派到已安装 runtime，benchmark 增加共享鉴权发现与前置 auth probe，Realtime 连接在 `finally` 中关闭。这些改动不改变 ASR/TTS 推理图或模型权重。
2. 因此 v2.0.3 相对 v2.0.2 的 RTF 大幅下降不能归因于“v2.0.3 推理优化”。最可能的解释是两轮的实际运行态/预热时机/runner 细节和本机背景条件不同；资源峰值也显示 light HTTP 反而上升 9.9%，与“整体硬件或模型全面变快/变省”不一致。
3. v2.0.3 本轮使用同一 manifest/schema、固定 fixture、同一机器，并显式 warm-up 后再测 Realtime；所以它是当前发布可复现基线，但不是对 v2.0.2 历史单轮数据的实验室级因果重放。若要冻结性能回归门值，下一步应在同一 runner 中连续重复两版本并预先固定噪声带。
4. `balanced/light` CustomVoice 的返回 PCM 时长有自然波动（short 约 4.08–5.04s、long 约 14.72–16.72s）；报告 RTF 已按每次实际输出时长计算，但 TTS 延迟变化不能单独解释成模型计算变化。
5. 未预热的额外质量 Realtime 复核中，第一 session TTFA 为 1.238s，后两次约 33ms；这验证了 profile 切换后的首次 TTS 加载成本。正式表使用显式 warm-up 后的 3 session，不把该 cold 观察混入 warm p95。

## 运行效率与可靠性改进固化

- CLI 的 `service preflight`、`profile apply/rollback`、`setup` 在带 `--app-home` 时统一执行 active `runtime/current/.venv/bin/python -I -m speechrail`；managed runtime 不可用时 fail closed，不再从源码 checkout 误跑 preflight 或切档。
- benchmark、MCP 与独立 ASR/TTS/Realtime 客户端共用 `resolve_api_key`：非空环境变量优先，其次自动读取 managed app home 的私有 `config/.env`；不 `source` 文件，不把 key 放入命令参数、日志或结果。基准开始先调用只读 auth probe，401 在任何推理前停止。
- 切档前、每档开始前和最终恢复后都用 listener/ESTABLISHED 快照与鉴权 `/metrics` 核对外部 Realtime session、batch/realtime active request；外部 Sona 必须由客户端自行停止，不能把 `backend_busy` 误判为候选 profile 失败。本轮 Sona 停止后复核为零活动连接。
- GitHub CI 的 native build 改为仅在 Darwin 执行，macOS hosted runner 统一到 `macos-15`；该修复已在 `2e2920e` 的 CI run `34257206587` 上验证 Ubuntu 与 macOS jobs 均 success。

## 限制与未验证

- 未执行独立 CER/WER、VAD FAR/FRR、MOS/ABX、speaker embedding、跨重启音色稳定性。
- 未执行 4 workers × 8 requests 吞吐、长时 soak 或并发上限专项；Realtime 仅覆盖显式 warm-up 后连续 3 session。
- v1.13.0 与 v2.0.2 的历史数字只用于方向性对照。v2.0.3 当前轮的 RTF 优于 v2.0.2，但代码差异没有修改推理实现，不能把单轮差异写成代码优化收益。
- 未把任何报告值同步到 README；性能索引会更新，README 按项目约定保持不变。

## 复现

原始制品在仓库外，命令中的 `$APP_HOME` 仅表示本机 managed app home：

```bash
APP_HOME="${SPEECHRAIL_APP_HOME:-$HOME/Library/Application Support/SpeechRail}"
uv run speechrail service preflight --app-home "$APP_HOME"
uv run speechrail profile apply quality --app-home "$APP_HOME" --yes
uv run python examples/perf/bench_profiles.py \
  --base-url http://127.0.0.1:8201 \
  --app-home "$APP_HOME" \
  --manifest <external-manifest.json> \
  --profile quality \
  --phase warm \
  --output <external-quality.json>
uv run python examples/perf/bench_realtime.py <external-16khz-pcm> \
  --sessions 3 --app-home "$APP_HOME"
```

正式发布前按 `quality → balanced → light → quality` 串行切档；每次切档前后检查外部连接和 profile identity，并在最终恢复后复查单 listener、`/health`、`/readyz`、`/v1/models`、`/v1/voices`、公共 smoke 与 `/metrics`。
