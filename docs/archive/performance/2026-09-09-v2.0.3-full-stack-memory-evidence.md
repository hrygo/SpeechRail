# v2.0.3 全链路内存证据与三档场景基准

日期：2026-09-09  
版本：`v2.0.3`  
状态：**有条件通过**

本轮三档功能场景全部通过。短生命周期 CoreML 分人进程改用 incarnation/active-window 口径后，C/D/E 的有效窗口均已闭合；全局采样仍如实保留 transition，不把跨身份峰值合并成一个伪造的全局 complete。最终运行态已恢复 `quality`。

## 1. 范围与环境

- 设备：Apple Silicon M5 Max，macOS `26.5.1`，物理内存 `128 GB`。
- 服务：managed runtime，单实例、单 ASGI worker，测试期间隔离外部 Sona 连接。
- 档位：
  - `quality`：ASR `1.7B q8`；TTS `1.7B VoiceDesign q8`。
  - `balanced`：ASR `1.7B q8`；TTS `0.6B CustomVoice q8`。
  - `light`：ASR `0.6B q8`；TTS `0.6B CustomVoice q8`。
- 输入：同一份 10 秒真人 PCM/WAV fixture。
- 采样：每档行为场景 N=5，资源采样间隔 `0.1s`；生命周期场景额外执行 10 次连接关闭循环和 600 秒持续会话。
- 工具：`examples/perf/benchmark_scenarios.py` schema v2、resource monitor schema v3、共享鉴权 resolver；原始 JSON 保存在仓库外，不提交音频、日志或凭据。
- 执行策略：A–D 按新 schema 重新执行 N=5；E 独立执行 10 次 close + 600 秒 soak；每档的 `scenario_ids` 已写入外部 JSON，避免工具修复时重复浪费完整 soak。

本报告将三个维度分开：`scenario_coverage`（行为是否执行并通过）、`sample_completeness`（资源证据是否覆盖完整）和 `resource_budget_verdict`（是否可以作预算结论）。三者不能互相替代。

## 2. 场景结果

| 场景 | 实际路径 | `quality` | `balanced` | `light` |
|---|---|---:|---:|---:|
| A | manual Realtime ASR → TTS | 5/5 通过 | 5/5 通过 | 5/5 通过 |
| B | `server_vad`（含静音尾）→ ASR → TTS | 5/5 通过 | 5/5 通过 | 5/5 通过 |
| C | REST `gpt-4o-transcribe-diarize` + `diarized_json` | 5/5 通过 | 5/5 通过 | 5/5 通过 |
| D | `server_vad` + Realtime diarization + TTS 共存 | 5/5 通过 | 5/5 通过 | 5/5 通过 |
| E | 10 次连接关闭循环 + 600 秒持续会话 | 11/11 通过 | 11/11 通过 | 11/11 通过 |

没有场景行为错误、超时、取消泄漏或残留 session/governor 状态。C 的匿名 speaker label 符合当前服务契约；D 实际收到分人和对齐事件后仍完成 TTS。上述结果与资源窗口证据均通过；但 8 GiB 目标仍需目标低内存设备验收，不能由本机 128 GB 设备替代。

## 4. 资源证据限制

- A/B 的物理角色为 `host-fastapi`、`batch-asr`、`tts`，全局与 active-window 采样均完整。
- C/D 每档均得到 5 个预期角色完整的 active windows；跨 session 的 PID/start-time transition 使全局 `sampling_complete=false`，但不影响各自 incarnation 内的有效 peak。任何 active window 内部缺样仍会使该 window fail closed。
- E 每档均为 11/11 行为通过、11 或 12 个 active windows 完整捕获 `diarization`；close 后增加 1 秒有界 settle，避免把服务端清理窗口误报为产品 `backend_busy` 重试。
- 当前 `resource_evidence_verdict`：A/B=`complete`，C/D/E=`active_window_complete`；未跨身份相加，未把 transition 边界伪装成全局 complete。

## 5. 结论、ROI 与后续决策

### 已交付

1. P0：资源采样不再因丢失进程/空 tick 而错误判定 complete；角色、身份、相对时间和 transition 进入 schema v3。
2. P1：公共 runner 覆盖 VAD、REST 分人、Realtime 分人共存、TTS 和生命周期；active-window incarnation 证据、共享鉴权发现、错误快速失败和有界 close-settle 已固化；fake HTTP/WebSocket 回归已补齐。
3. 三档 A–E 证据已完成：A–D 新 schema N=5，E 10 次 close + 600 秒 soak；最终 profile 恢复 `quality`；报告不提交原始音频、token、日志或模型路径。

### 本轮不做 P2 运行时字节 reservation

当前没有压力、swap、OOM 或持续增长证据。`light` 的 D active-window peak 为 `8.02 GiB`，说明不能在目标低内存设备验收前承诺 8 GiB；但本轮主机是 128 GB，不能把该结果直接当作目标设备 pressure/OOM 证据。直接引入动态 reservation 的成本包括生命周期计费、共享 ASR/aligner 重复计费、嵌套资源获取和误拒绝风险，当前 ROI 仍不足。

下一步最高 ROI 是在真实目标低内存设备复核 `light` 的 D 全链路峰值，并以本报告的 active-window 结果作为基线。只有在目标设备上预算稳定超出、pressure/OOM 可复现或出现持续增长时，才开启 P2；优先修复具体泄漏/无界缓冲，再评估 reservation。当前 P2 决策：**不实施动态 byte reservation，继续跟踪目标设备证据**。

因此，`light` 的“8 GiB 能力”本轮保持 `unset`：D 的观测值已接近并略超 8 GiB，但当前设备是 128 GB，既不能证明目标设备一定超限，也不能证明它能稳定满足 8 GiB。

## 6. 与旧报告的可比性

旧版 v2.0.3 HTTP 流程曾记录 `quality/balanced/light` 约 `6779.1/5919.6/4450.9 MB`。旧流程未以本轮统一口径覆盖 VAD、CoreML 分人、对齐和生命周期窗口，且场景、角色发现和完整性 gate 不同；这些数字保留为历史证据，不与本轮 A/B 或未闭合的 C/D/E 直接作回归或绝对上限比较。

## 7. 复现与产物

全套默认执行 A–E；只重测受工具影响的 A–D 时显式选择场景，生命周期 E 单独保留 10 次 close + 600 秒 soak。将 `<APP_HOME>`、fixture 和输出路径替换为本机授权路径：

```bash
uv run --extra dev python examples/perf/benchmark_scenarios.py \
  --base-url http://127.0.0.1:8201/v1 \
  --profile light \
  --pcm-file '<APP_HOME>/benchmarks/fixtures/human-10s.pcm' \
  --audio-file '<APP_HOME>/benchmarks/fixtures/human-10s.wav' \
  --app-home '<APP_HOME>' \
  --iterations 5 \
  --lifecycle-loops 10 \
  --soak-seconds 600 \
  --sample-interval 0.1 \
  --scenarios E \
  --output '<APP_HOME>/benchmarks/20260909-v2.0.3-full-stack/light.json'
```

三档脱敏 JSON 产物位于本机仓库外的 `benchmarks/20260909-v2.0.3-full-stack-v2/`，分别记录 A–D 与 E 的 `scenario_ids`；本仓库只保存本报告和可复现工具，不保存 raw benchmark artifact。
