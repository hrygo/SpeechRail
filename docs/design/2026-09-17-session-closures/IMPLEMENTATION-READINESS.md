## 0. 结论

**三处断点已全部裁决（用户 2026-09-18：「360」+「采纳所有建议」），阶段 0 关闭，可以从阶段 1 开工。**
断裂原本不在闭环内部——三条闭环的每一格都有画板、每一块画板都能走通；断裂在**稿与工程契约之间**：

| # | 断点 | 决定 | 落地状态 |
|---|---|---|---|
| 1 | 会话页侧栏在稿里有 **320 / 420 / 300 三个宽度**，而应用的列宽只有 `inspectorColumnWidth = 360` 一处声明 | **D7 = 360** | ✅ 已改稿：`SESSION_SIDE_W = 360` + `NUMBER_TOKENS` 里的 `size/inspector`，15 处列宽归一（§1 第 13 行） |
| 2 | 记录库的产品口径有了（P8、§9、三块记录库画板），但**表结构、库文件位置、迁移与备份方式没有** | **D8 采纳建议**：系统 `SQLite3`、`Application Support/SpeechRail/sessions.sqlite3`、§15 建表、`user_version` 迁移、`VACUUM INTO` 备份 | ✅ `SESSIONS-SPEC.md` §15 已从「草案 · 待裁决」改为「已采纳」 |
| 3 | 稿与规格都写「**全局**快捷键」，而 SwiftUI 的 `.keyboardShortcut` 只在 App 前台生效，仓库里也没有任何全局热键机制 | **D9 采纳建议**：Carbon `RegisterEventHotKey`，不做全局事件监听 | ✅ 写进 `SESSIONS-SPEC.md` §13 |

同一批被采纳的还有 D2（快捷键重排：创作页不动）、D3（不做镜像提词）、D5（阶段 9 同步边界文档）、
D6（大模型端点留空、不猜地址）。**D1–D9 全部结清**，`SESSIONS-SPEC.md` §13 是唯一账本。

**还剩一条待裁决（D10，§13.1）**：**目录列**的宽度还没有归一——会议列表 260、字幕记录库 240、
助手记录库 232、开发者文档主题目录 272，而应用侧只有 `modelProfileListWidth = 280` 一档。
它与 D7 同类，但多牵一层（列表里的搜索框 228 / 208 / 200 与行文本宽度都跟着列宽走），
**不阻塞阶段 1/2**，建议下一轮连同 Figma 实跑一起归一为 280。

**旅程层已经核过一遍（2026-09-18 第四轮）**：按用户故事走 8 条路径，发现两处**路径断点**
（助手没有长期信息的面、会议没有中断后的态），两处都已补成画板；另外 6 处是规格口径
（导出命名、检索范围、记忆规则、破坏性确认、抢麦克风话术、中断四类）已补进 `SESSIONS-SPEC.md` §16。
**旅程的步骤表在方案正文里**（`SESSIONS-SPEC.md` §16.2.1–§16.2.6，2026-09-18 第六轮并入；
每个阶段「结束时能走通哪条旅程」见同文件 §12）；逐条对账与可测判据在
[`USER-JOURNEYS.md`](USER-JOURNEYS.md) 的 §9 / §10。**它不改变阶段 1 的开工条件**：
补的全是阶段 2/5/6 的东西。

另外，用户本轮更早给的一条约束**已经落进稿**：**新会话开始后不允许换人设**（§1 第 1 行、
`SESSIONS-SPEC.md` §14.4）。

**第五轮（2026-09-18）不改开工条件，但改两处编码输入**：① 大模型依赖的**接口形态**被写死为

### 2.2 需要新增的（4 个组件 + 1 个抽取 + 1 个窗口）

| # | 名称 | 稿上的位置 | 为什么现有组件不够 |
|---|---|---|---|

## 3. 状态 → 契约核对

逐条对着 `contracts/realtime-openai.md` 与 `contracts/openapi.yaml` 核（2026-09-17）。

| 状态 | 契约事实 | 结论 |
|---|---|---|
| 分人三态（档位不支持 / 已启用 / 降级） | `session.speechrail.diarization.enabled` 只在首个 PCM 前协商；回显 `{enabled:true, version:1, max_speakers:4}`；「最多四名匿名说话人由固定模型约束」；`speechrail.diarization.status` 在 `diarization_overloaded` / `diarization_invalid_output` / `finalization_timeout` 时触发单次 active→degraded；`diarization_not_available` 是 profile 不可用时的错误码 | **一致**：规格写的 4 位、三态、降级后正文照常，全部有契约依据 |
| EOF 屏障 | `speechrail.diarization.finish` → DRAINING → `speechrail.diarization.done`（携带 `through_sample`、`status: complete \| degraded`、`last_update_sequence`） | **一致**：会议「整理中」这一态就是等这个 done |
| 说话人改名 | 契约的 `attribution_units` 字段「在归属修订中不可变」；正文同样不可变 | **一致**：改名只能是 App 侧元数据（§15 的 `speaker_name`），改不动服务端正文 |
| 换音色 | `session.update.voice`「接受已注册 voice 与 13 个 OpenAI 标准 voice 别名」；`voice_not_found` / `voice_not_available` / `invalid_voice`「失败均保持 session 可用」 | **一致**：稿上「音色下一句生效 + 被拒时这一句仍用旧音色」有依据 |
| 实时对讲打断 | `speech_started` → 原子 `response.cancel` → `realtime_vad_bargein_cooldown_ms`（默认 250ms） | **一致**：稿上写的「冷却 250 ms」是契约默认值 |
| 换设备 | 「输入为 PCM16，支持 `16000` 或 `24000` Hz…**首个 PCM 后不得改格式**」 | **一致，且这是硬约束**：换设备只能重开会话（§10 第 3 条） |
| `backend_busy` | 是正常返回，session 保持可用 | **一致**：§7.1 不把它当异常态 |
| 24 kHz 采集格式 | 支持 24 kHz 并在会话内有状态降采样到内部 16 kHz | **一致**：稿上「采集格式 24 kHz → 内部 16 kHz」说的是服务侧行为，不是 App 要自己做降采样 |
| 本机音频（进程 tap） | **契约里没有这一条** | **一致地缺席**：它是 App 的本地能力，服务只看到 PCM。§10 已按这个口径写 |
| 内心 OS | **契约里没有这一条** | 同上：走用户自己的大模型，App 编排 |
| 会议中断（2026-09-18 补） | 契约里有 `backend_busy` 与 `finalization_timeout`，但**没有**「服务重启后这一段怎么办」 | **一致地缺席**：中断是 **App 侧**的状态机（§16.7），服务只负责「重连后能不能继续喂 PCM」。所以 R1 的两处表落在 App 的库里，不等服务 |
