# SpeechRail v1.13.0 高 ROI 优化实施方案

> **For agentic workers:** 实施时使用 `executing-plans`，按可独立验收的批次推进；默认串行，不因本文自动委派、提交、发布或操作服务。复选框表示未来工作，未勾选项不是已实现能力。

**Goal:** 用最少的新接口和运行机制，消除当前 TTS 无界等待、失败不可归因、错误内存准入依据及音色写入损坏风险。

**Architecture:** 沿用现有 ASGI、ResourceGovernor、TTS worker 锁、worker abort/reap、音频 validator 和原子文件写入。修补现有执行路径；不引入第二套调度器、管理控制面或模型运行时。

**Tech Stack:** Python `>=3.12,<3.13`、uv、FastAPI/Starlette、asyncio、pytest、现有 MLX worker IPC。

**Spec:** 本文的“当前版本事实”和“设计约束”构成本轮需求；公共行为以 [OpenAPI](../../../contracts/openapi.yaml) 与 [Realtime 契约](../../../contracts/realtime-openai.md) 为准。本文独立从当前源码生成，不继承旧优化方案、旧架构提案或历史 issue 的任务清单。

## 2. ROI 决策

ROI 按“已证实影响 × 覆盖路径 ÷ 实现和持续维护成本”作定性排序，不伪造货币收益或工期精度。

| 路线 | 收益与成本 | 决策 |
|---|---|---|
| 现有路径增量修复 | 直接保护失败请求和用户音色；复用测试、worker、配置及部署流程 | 采用 |
| 运维功能扩建 | activity/drain 协议、warmup API、GC、压力探针都增加新状态和兼容面 | 本轮不做 |
| 更换模型/runtime 或性能重构 | 质量、兼容、迁移成本高，尚无当前瓶颈证据 | 本轮不做 |

两条独立交付线，不相互捆绑发布：

| 批次 | 范围 | 相对成本 | 可证明的收益 | 依赖 |
|---|---|---|---|---|
| R1 | 请求结束日志、TTS 分阶段诊断、驻留可见性 | 小—中 | 正常、异常、取消都可按请求归因 | 无 |
| R2 | REST TTS 总 deadline、实际 TTS 准入、取消后恢复 | 中 | 等待可界定，物理 worker 不被提前复用 | R1 提供归因；修复本身可独立测试 |
| R3 | 移除无依据的跨模型 overlap | 小 | cache/memory limit 不再制造“预算已验证”假象 | 无，R2 后联合验收 |
| V1 | 损坏 store 拒写、同 ID 替换保全旧音频 | 中 | 阻止覆盖丢失及旧 metadata/新 WAV 错配 | 独立，不阻塞 R1–R3 |

R1–R3 是本轮推荐首包。V1 是独立数据安全补丁，不扩大为音色存储重构。每批达到退出条件后即停止扩展，不以“顺便补齐”增加功能。

## 3. 设计约束

- 保持一个 SpeechRail 服务、一个 ASGI worker、一个共享 ASR worker 和一个 TTS worker。ASR batch/streaming 冲突继续为 `backend_busy`。
- 不更换模型、量化、音色、分句算法、采样率或 vendor 依赖，不改变三档的架构。
- 不重定义 `tts_ready`、`/readyz`、`tts_warmup_on_start`、`worker_lazy_load`；不默认延长 `request_timeout_seconds`、关闭 eviction 或启用 eager load。
- 不向请求路径加入网络、下载、切档、磁盘扫描或系统压力子进程。
- 日志不含请求正文、音频、Authorization、完整 prompt/transcript、voice 自由值、绝对模型路径或原始 vendor 异常文本。指标不使用 request ID 标签。
- 所有公共行为变化同步契约、回归和专业用户文档；README 不在本轮写入范围。
- 文档制定授权不包含后续代码实施、部署、Git 提交、远端操作；后续已获得的具体授权持续有效，不重复索取。

**Interfaces 与边界：**
- 继续使用唯一公共 `request_timeout_seconds`。REST payload 校验通过、进入合成用例时设 `expires_at = loop.time() + request_timeout_seconds`；计入准入、worker 加载、生成、编码、输出发送。不借此修改上传 ASR 的超时语义。
- 新增内部 `await_until(operation: Awaitable[T], expires_at: float) -> T`。一个 expires_at 在请求内传递，不重置。每次 await 的 timeout context 必须在 yield 前退出，避免 generator 跨 task 消费造成 timeout context 归属错误。
- 在既有 `ResourceGovernor._can_admit()` 增加 TTS 条件：已有 active TTS 时新 TTS 留在既有有界等待队列。`run()` 与 `reserve()` 自动共用规则；不新增 WorkerSlotRegistry，不改变 ASR 多会话容量、FIFO、aging 与 realtime 预留策略。
- REST 首包前超时沿用 `503 backend_timeout`；响应头之后关闭流，记失败，禁止写入第二份 JSON 响应。Realtime 保留既有总 deadline、`backend_timeout` 和 failed `response.done`；终态发送若也阻塞，关闭连接，不宣称客户端已收到终态。
- deadline 到期先中止交付，再清理底层 iterator/encoder/worker，最后释放准入。复用现有 abort/shield/reap；不得把 `aclose()` 的失败吞掉后立即借出物理 worker。若进程清理无法确认，隔离该 worker、拒绝再次启动并报告恢复动作，不在 HTTP 请求内循环重启。

- [ ] **1. 建立失败测试。** 总预算测试使用以下可执行形状；第二次等待不能获得全新预算：

  ```python
  import asyncio
  import pytest
  from speechrail.application.deadline import await_until

  def test_absolute_expiry_stops_waiting() -> None:
      async def scenario() -> None:
          expiry = asyncio.get_running_loop().time() + 0.05
          await await_until(asyncio.sleep(0), expiry)
          with pytest.raises(TimeoutError):
              await await_until(asyncio.sleep(1), expiry)
      asyncio.run(scenario())
  ```

  以上先证明绝对到期会中止等待。另测将同一 expiry 设为过去时间后连续调用，两次均不得进入需要等待的操作；检验期限确实没有重置。路由测试使用 Events 控制慢首包、持续小块但总时长超限、卡住的 send、启动失败、encoder 卡住和排队取消。PCM、MP3 容器路径、preview、Realtime 均需覆盖；只验证协程 sleep 不算路由完成。

- [ ] **2. 实现最小 deadline helper。**

  ```python
  import asyncio
  from collections.abc import Awaitable
  from typing import TypeVar

  T = TypeVar("T")

  async def await_until(operation: Awaitable[T], expires_at: float) -> T:
      async with asyncio.timeout_at(expires_at):
          return await operation
  ```

  用于准入、逐次 `anext()`；ASGI send wrapper 从同一请求 state 读取 expires_at 并限制发送。不要把每次 `anext()` 的超时设成完整 `request_timeout_seconds`。底层 I/O timeout 继续作为防线，总预算先到就取消并清理。R1 阶段记录说明超时发生位置，暂不增加 startup/first-output 多套公共配置。

- 保留 v1 同 ID 替换语义，不新增重复 ID 拒绝。clone 新音频写为受控的 `<voice_id>.<uuid>.wav`，旧 metadata 中合法的 `<voice_id>.wav` 路径仍可读取。JSON schema 和 `audio_path` 字段保持兼容。
- mutation 在一个锁内重新读取/验证 registry、构造副本、写新 WAV、原子替换 JSON，最后发布内存视图；异常不能把未提交副本暴露给读者。当前单服务内锁覆盖全部 create/replace/delete；外部手工编辑要求先停服务，不新增多写者产品承诺。
- 新增同步上下文管理器 `VoiceRegistry.lease_profile(voice: str) -> Iterator[VoiceProfile]`，锁内取当前不可变 profile 并递增对应音频引用计数，退出时递减；不持有 mutation 锁跨越生成 await。TTS adapter 在解析 binding、发送 ref_audio 前取得同一个全局 registry 的租约，在 completed 或 abort/reap 后释放。`resolve_binding()` 增加可选的 `profile: VoiceProfile | None` keyword，使用租约取得的快照，避免二次解析时读到另一版本。纯能力查询继续使用原调用形式。
- JSON 是唯一提交点。新 WAV durable 后再提交 JSON；metadata 指向新 WAV 前不能删旧 WAV。替换成功后，旧音频若无读者立即清理，否则在最后一个租约释放后清理；清理失败保留文件并记录有限错误码，不回滚已经提交的新 JSON。
- 删除在同一 registry 锁内检查目标 voice 的所有在用版本；有读者时不改 JSON/音频，抛 `VoiceInUseError`，HTTP 返回 `409 voice_in_use` 可重试。没有读者时提交删除并清理受控音频；清理失败返回明确的 `503 voice_store_unavailable`，不宣称成功删除，也不为补偿重新发布过期 voice。操作手册说明登记可能已删除而音频清理失败的恢复方法，不把逻辑删除伪装成物理删除。
- 原子 JSON replace 后若目录 fsync 抛错，提交结果可能不确定：保留新旧音频，重新读取核对磁盘；无法确认则 store unavailable。不能一律在异常中 unlink 新 WAV。crash 后允许有未引用文件，禁止旧 metadata 指向被删除/覆盖的音频。
- 0600 文件、0700 专用 store 目录；不 chmod 任意已有共享父目录，不改变仓库外未知目录权限。权限不满足且不能在专用目录安全修正时拒写并报告。

## 5. 不进入本轮的功能与重新进入条件

| 不做项 | 原因 | 重新考虑的必要证据 |
|---|---|---|
| activity API / profile idle gate / drain lease | CLI 跨进程事务较复杂；只读快照不能保证无竞态 | 当前真实使用中出现切档打断需求，并明确停服/失败恢复语义 |
| service warmup / wait-ready 新命令 | 当前问题优先是等待边界和归因，不是缺命令 | 冷启动已实测为主要延迟来源，且当前启动方式不能满足消费者 |
| 默认 eager TTS、延长驻留或增大 timeout | 会增加内存或掩盖故障；已有 vendor warmup | 同档同语料冷/热对照和实际交互空闲分布证明净收益 |
| memory_pressure/vm_stat 动态控制与峰值配置库 | 平台、刷新、迟滞、模型身份失效均有维护成本 | 保守策略确实成为性能瓶颈，存在匹配 artifact/runtime 的峰值证据 |
| journal/GC/自动 orphan 回收 | 增加文件删除与恢复状态机；V1 单提交点已保护数据 | 存储增长成为实际问题，并具备引用/并发 reader 安全回收方案 |
| Realtime 协议扩展、ASR 对齐缓存、TTS 分句/音色算法重构 | 独立消费者契约与质量验收范围 | 当前消费者失败用例或阶段测量明确指向该问题 |

## 6. 验收、收益判断与回退

### 6.1 代码验收

每批先失败回归、最小实现、针对性测试，再按项目要求跑完整 gate。最终候选包含哪些批次，就在那些批次全部落地后重新跑 gate，不能复用中间批次结果冒充最终结果：

```bash
uv run --extra dev pytest
uv run --extra dev ruff check src tests
uv run --extra dev mypy src
npx @redocly/cli lint contracts/openapi.yaml
git diff --check
```

新日志的 steady-state 成本用 fake backend 固定请求集比较：相同进程条件下测三轮中位数，记录日志 sink；若 p50 额外开销超过 1 ms 或吞吐下降超过 5%，调查后再接受。这是候选工程门，不是模型性能承诺。

### 6.2 运行态证据链

仅在已有授权覆盖具体操作时执行，依据 [本机部署 SOP](../../../.agents/skills/speechrail-local-deploy/SKILL.md)、[发布 SOP](../../../.agents/skills/speechrail-release/SKILL.md) 与 [性能 SOP](../../../.agents/skills/speechrail-perf-benchmark/SKILL.md)。选择哪个 profile/几档测试由实际变更与 SemVer 决定，不在本方案假定本机档位。

1. **先记录基线身份。** 分别记录基线和候选的源码 commit、wheel hash、runtime release 身份；对照时固定 vendor lock hash、模型 artifact 指纹、profile、fixture hash、预算与 cold/warm 定义。已有基线只有相关非变更条件匹配才复用。记录基线的 warmup/timeout 行为，不能只凭 issue 历史统计。
2. **构建并核验候选。** 按 SOP 停旧实例、隔离 release preflight、切换 current；确认启动的进程来自候选 release。`/health.version` 相同不足以证明同一构建，必须能关联 wheel hash 与实际启动路径，报告只保留路径外的身份值。
3. **固定场景对比。** 冷/热 TTS、两个 TTS 竞争、REST/Realtime 交替、取消后下一请求、ASR+TTS 各自负载。记录 startup、first PCM、总交付、queue、cleanup、reload/abort、成功/失败分母及同 tick 物理内存。
4. **先廉价筛查，再扩大。** 每个代表场景 5 次只作功能筛查；通过后才进行至少 100 次代表性交互来分析 p95/失败率，并声明 cold 与 warm 各自样本量。没有冷启动足够样本时不发布 cold p95。针对性内存/质量验收按 SOP，不运行无目的的大矩阵。
5. **分别判定收益。** R1 看关联完整性；R2 看是否有界、取消恢复与排队，不能用更大 timeout 降低 503；R3 看策略正确性并如实报告串行代价；V1 看故障注入后的数据一致性。相同语料与音色质量不可退化；没有听感证据时质量 gate 保持 unset。
6. **不达标即停止扩展。** 首包未改善但正确性通过，可以发布可靠性修复并明确没有性能收益；若成功率、恢复或质量退化，阻止对应批次发布。不要为凑改善率更换语料、剔除超时或改变模型。
