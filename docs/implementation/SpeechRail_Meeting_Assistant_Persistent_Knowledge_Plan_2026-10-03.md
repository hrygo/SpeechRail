# SpeechRail 会议助手：用户旅程与持久知识库优化方案

> **产品目标：会议结束不是内容的终点。让每场会议形成由用户拥有、长期保存、能够核对和修订、跨会议检索与复用的知识资产。**
>
> **关键区分：自动保存决定内容是否留下；用户核对决定内容的可信状态；全文/向量索引只决定怎样找得更快。三者不能混为一谈。**

## 0. 决策摘要

建议保留现有本地采集、Realtime ASR、SQLite 会话库和多版本纪要基础，沿着“会前准备 → 会议记录 → 转录核对 → 纪要生成 → 知识沉淀 → 跨会议使用 → 备份恢复”的完整旅程演进，不另起一套云端会议平台，也不把知识库简单等同于向量数据库。

### 0.1 本方案的六项核心决策

| 决策 | 推荐方案 | 不采用的默认做法 |
|---|---|---|
| 纪要的归属 | 每场会议自动拥有独立、持久的知识文档；没有核对也保存为待核对稿 | 每次必须再点“加入知识库”，否则生成结果随页面消失 |
| 纪要的可信度 | 原始转录、人工修订、AI 归纳、用户补充分别标识；重要结论可定位到来源 | “JSON 合法”“生成完成”直接等于事实正确或参会者已同意 |
| 数据本体 | 复用 `SessionStore` 单一权威写入口；保存结构化内容、来源快照和版本；Markdown 是可移植阅读副本 | 把 Markdown、向量索引、UI 状态各自变成一份相互覆盖的权威 |
| 检索方式 | 先做跨转录、纪要、决策、行动项的本地全文检索；经评估再添加语义召回 | 先装重量级向量库，或者只把摘要嵌入后删除来源 |
| 再生成与修订 | 新候选版本不覆盖用户采用版本；来源变化使旧结论标为需复核 | 新一次失败取代旧的可用纪要；修改转录后旧答案继续冒充最新 |
| 持久与退出 | 默认不因时间、升级、换模型、清缓存而删除知识；提供验证过的备份、恢复、开放格式导出和明确删除 | 把文件存在当成永不丢失；把云同步当备份；完整删除时暗中保留引文副本 |

### 0.2 首个可交付版本必须包含什么

首个“持久知识库”版本必须同时交付：**可靠封存、版本化纪要、来源引用、历史会议入口、基础检索、选定版本导出、备份恢复**。语义检索和跨会议 AI 问答可以后置，但持久保存不能后置。

研发顺序：先修复会议来源和纪要状态的真实性，再提供可持续积累的知识库，最后增加高级检索与知识复用。不要先美化纪要页，再把保存、来源和恢复当作基础设施补票。

### 0.3 审查边界与证据口径

本方案固定于 `main @ be75055cc0a5f7f044ae56c955896812a1d69915`。阅读了会议会话、纪要生成、私密问答、会议视图、SQLite 数据层、协调器、相关契约以及可复用的持久化测试。通过 GitHub Connector 读取源码；不把远程源码读取称为本地完整 clone。[^C01][^C02]

本轮没有运行 macOS App、麦克风、系统音频、ASR/LLM/TTS、UI 自动化、性能基准或仓库测试。下文的“源码事实”表示在固定提交中看到该实现；“静态风险”表示由代码路径推导、需回归复现；“设计建议”是拟新增行为；候选指标不是现有成绩。

工作包 `MA-01`～`MA-22` 和验收场景 `MC-01`～`MC-80` 均为**本文内部编号**，不是已创建的 GitHub Issue。方案、skill 和文档步骤不授权实施、推送、安装、录音或调用收费服务。目标仓库自身规则优先于通用 Git 流程。[^C02]

## 1. 当前基线：已有能力、缺口与必须先修复的问题

### 1.1 已有能力应继续复用

`MeetingSession` 已支持麦克风、所选 App 系统音频和混合来源，会话中断、恢复、说话人标注、会议结束后整理；会议不承载 TTS。`MinutesGenerator` 已请求结构化输出，并支持纪要版本、排队、租约和停止入口。`SessionStore` 将记录放在 Application Support，采用 SQLite actor 单写者、WAL 和版本表，已有转录检索与 `VACUUM INTO` 一致性备份。它们是基础，而不是需要推倒重来的历史包袱。[^C03][^C04][^C05]

现有 `InnerOSSession` 将私密问答与会议正文分开，默认不进入纪要；这是正确的隐私边界，后续知识库不能把它们自动合流。当前读取到的公共记录搜索主要是 `line.text LIKE ...`，不能据此声称已经具备纪要、行动项和跨会议知识问答。[^C06][^C05]

### 1.2 重要源码发现

| 编号 | 源码事实与推导 | 用户影响 | 处理方向 |
|---|---|---|---|
| F01 | `MinutesDocument` 的决定是字符串、待办是 owner/task/due 字符串；未表达逐项来源、源版本、审阅状态；最后渲染为 Markdown 存储 | 好读但难验证、难追踪，不能可靠回答“这条结论是谁说的、后来改了吗” | 结构化纪要 V2 + 不可变来源快照 + 引用索引 |
| F02 | `markdown(from:)` 对空输出或无法解码的输出返回提示/原文；`run` 之后仍调用 `finishMinutes` 并置 `.ready` | 空内容或结构错误可能表现为整理成功 | 拒绝、截断、空输出、结构失败分别建模；保留失败候选但不标成功 |
| F03 | `enqueueMinutes` 先清所有旧 `is_latest`，再插入新版本，已读方法内没有包围两步的事务；`latestMinutes` 选最新尝试，不要求 ready | 插入失败可丢失最新指针；重生成失败挤掉旧可用版 | 同一事务；最新尝试、最新可用、当前采用三个指针分离 |
| F04 | `recoverPending` 调用 `generate`，而 `generate` 会新建版本；远端 response ID 只在内存；认领、完成没有执行者 fencing token | 重启可能不是续跑原任务，而是新开一版；旧任务迟到结果可能改状态 | 按 job ID 恢复，持久化远端身份，租约代际比较提交 |
| F05 | `InnerOSSession` 先存 generating，再以同一个 ID 存 ready/failed；Store 是普通 INSERT，表 ID 是主键，调用处吞错 | 在前次 INSERT 成功时，后次写入会发生主键冲突；UI 可有答案而重开库仍是 generating | 建行一次，终态 UPDATE/upsert 校验身份；答案和证据事务提交 |
| F06 | 私密问答按模型给的 ordinal 对行，不验证 quote 是否来自该行，`contentHash` 为 nil；“写进纪要”只改旗标，当前纪要生成只读 lines/names | 链接形式存在不代表引文真实；“已加入”与实际生成输入不一致 | 引文源文校验；显式用户补充输入通路；不把推测洗成会议事实 |
| F07 | 会议启动存在多处 await，但已读流程没有助手模块那样的生命周期/连接代际门禁；接收循环不带连接身份；去重集合只在新场清理 | 中止启动、快速重试、重连 ID 复用等情况下，有跨代污染或漏存风险 | 可注入生产编排 + 连接级 item 身份 + 每次 await 后检查所有权 |
| F08 | 会议 partial 为单一字符串，不跟随 item 身份；空 final 先清 partial 再返回 | 多 item 事件可串内容；用户看到过的半句可能无声消失 | item 级状态；未定稿片段保留为恢复材料，不用于正式纪要 |
| F09 | 当前行起止来自 final 到达的 Date 窗口；后续归属只补 timingQuality，不替换起止；渲染将 nil 起点写成 00:00 | 展示时间可能被误当真实发言时间；长期引用看起来精确但无该证据 | 观测时间与声学时间分字段；无声学证据用段落定位，不造 00:00 |
| F10 | 结束会等 `drainAndClear`，随后关闭并取消 pump；未见应用层“最后终态已写库”的独立屏障；协调器封存写入有 try? | 传输收尾不等于用户文本已持久化，不能仅据此说“已全部保存” | 传输水位 + 应用消费/保存水位，封存必须返回明确结果 |
| F11 | 历史会议信息分多次 await 更新；回看 body 有纪要时忽略文字记录页签；导出读 latest，未使用用户选中的旧版本 | 读错对象、页签看似没反应、所见版本与导出版本不一致 | 原子详情快照 + 选择代际 + 显式 export selection |
| F12 | 已读会议库卡片只显示 recent 的前 8 条；实时追加文本时无条件滚到底部 | 长期积累入口不足；回看/复制被新转录打断 | 会议知识库完整列表与搜索；按用户滚动意图决定跟随 |
| F13 | 库用 WAL + synchronous=NORMAL；删除 session 会级联删除 minutes 和来源；已有备份方法但不等于完整恢复产品 | 电源/系统故障耐久性、误删与恢复缺少清晰产品契约 | 强化提交耐久策略，知识删除语义，恢复验证与备份清单 |

F01～F04 来自纪要生成与队列方法；F05～F06 已核对调用、协调器转发和表定义；F07～F10 是需定向复现的生命周期与证据风险；F11～F12 来自视图具体路径；F13 中 NORMAL 的断电取舍由 SQLite 官方文档限定，不能扩写成“普通 App 崩溃就一定丢数据”。[^C03][^C04][^C05][^C06][^C07][^C08][^R15]

### 1.3 不要夸大审查结论

这不是“会议助手没有存储”“没有任何测试”或“所有纪要都会丢”的结论。代码已经有持久化和恢复基础，问题在于某些实际路径没有实现其注释和 UI 承诺。实施时先把这些路径写成可控失败/乱序回归，再修复；不要仅修改注释将错误行为合理化。

现有 `AssistantPersistenceTests` 使用临时 SQLite 目录、真实 Store 和固定行 ID 验证持久终态，可复用这种测试方式，但它并不证明会议生成链已经受覆盖。新增 Meeting/Minutes 测试必须编译和调用生产实现；先核实 SwiftPM 显式 source 清单和 Xcode 工程，不用一份仿制状态机代替。[^C09][^C10]

### 2.2 转成可执行原则

本方案采用四项工程原则：

**证据先于漂亮文案。** 先确定来源、缺口和版本，再渲染摘要；不能用 fluent prose 弥补没有发生过的决定。

**保存与 AI 服务解耦。** 记录和已有知识可离线打开、编辑、搜索、导出。没有 LLM 不影响记录；没有 embedding 不影响全文检索。

**长期状态有明确责任者。** AI 能提出行动项，用户能核对、修改、完成或取消；系统不能从下一次会议的沉默推断任务完成。

**持久性通过恢复证明。** 写进本机数据库是必要条件；独立备份、完整性检查、恢复演练与可读导出才构成可持续的知识资产管理。

### 2.3 为什么不从“向量数据库 + Chat”开始

本次最高 ROI 的缺口是来源、保存终态、版本与检索入口。一个拥有错误引文、被失败新版本遮住、无法恢复的文档，嵌入后只会更容易被错误引用。

推荐先让全文搜索可以命中“预算”“回滚”“3.5.6”“某个产品名”，并能打开正确的会议与版本；再用真实用户的概念性查询验证向量召回是否带来增益。采用 RRF 时融合的是排名，而不是将 BM25 和 cosine 原始分数当成同一尺度。[^R10][^R11]

## 3. 产品定位、知识类型与完整用户旅程

### 3.1 产品定位

会议助手是面向个人的**会议记录与知识工作台**。它帮助用户记下重要讨论、形成可核对纪要、追踪结论变化、为下一次讨论找回依据。不是会议主持机器人，不默认替用户发言、邀请参会者、通知负责人或自动向组织共享资料。

本轮不引入常驻监听、云端会议机器人、自动录像、跨会话声纹识人、未经确认的工具调用。继承项目当前会话 PCM 不持久化边界；新增的是文本与知识的生命周期，不是“顺手保存所有音频”。[^C02][^C11][^C12]

### 3.2 两条互通但独立的路径

**记录路径**：选来源 → 开始记录 → 结束并封存 → 自动保存会议文档 → 用户选择的纪要策略 → 阅读与核对。

**知识路径**：打开会议知识库 → 按关键词/项目/时间找内容 → 查原文和历史版本 → 引用、更新行动项、形成下次会议准备稿。

进入知识路径不申请麦克风、不连接 ASR、不占用会话设备。正在记录 A 时可以安全查看 B；查看 B 的任何修改、导出或重生成必须以 B 的文档身份为准，不能借用活动会议的全局 sessionID。

### 3.3 五类内容，不以“AI 记忆”混装

| 内容 | 本体 | 可信/使用边界 |
|---|---|---|
| 原始转录 | ASR final 原文与采集质量信息 | 忠实保存识别结果，不承诺它就是实际发言的无误抄本 |
| 人工校订 | 对原始内容的修订版本与修改者、时间、原因 | 不覆盖原始转录；能看修改前后 |
| 会议纪要 | 结构化归纳、结论、决策、行动项、未决事项与证据 | AI 待核对或用户已核对，不能等同所有参会人批准 |
| 用户笔记/私密问答 | 用户备注、问答、构思与草稿 | 默认私密；进入纪要须明确标为用户补充，不能冒充会议结论 |
| 派生检索数据 | 分块、全文索引、embedding、临时答案缓存 | 可删除重建；没有资格成为唯一知识来源 |

### 3.4 旅程验收地图

| 阶段 | 用户最关心的问题 | 页面核心任务 | 失败时必须保留 |
|---|---|---|---|
| 会前 | 能记到我和对方吗？内容会发到哪里？ | 选场景/来源、确认数据流、开始 | 用户标题、笔记、已选来源 |
| 会中 | 真的在记录吗？能暂时不记吗？ | 阅读当前转录、标重点、添加私人笔记 | 已落库正文、停记区间、手动控制 |
| 中断 | 哪一段没记到？如何继续？ | 选择恢复来源或结束 | 同一会议身份、已存行和断点 |
| 会后 | 纪要靠谱吗？有漏项吗？ | 核对决策/行动项，查看引文 | 原文、旧版纪要、失败候选与编辑草稿 |
| 长期 | 当时为什么这么决定？现在是否还有效？ | 搜索、按项目整理、比较与引用 | 来源版本、历史决定与修订记录 |
| 维护 | 换电脑、升级、误删后还能找回吗？ | 导出、备份、恢复、明确删除 | 可验证的备份与可读开放格式 |

## 4. 会前与会中：降低门槛，同时保证来源真实

### 4.1 会前页面

第一屏主动作“开始记录”，保留轻量标题和来源摘要。标题可为空、项目可稍后补；不要为了归档要求用户先完成复杂表单。

以场景帮助选择来源，但场景只是一组明确输入设置：

| 场景 | 建议预填 | 必须解释的边界 |
|---|---|---|
| 现场会议 | 麦克风 | 一只麦克风不保证分清每个人 |
| 在线会议 | 所选会议 App 系统音频 + 麦克风 | 只选麦克风可能漏掉耳机里的对方；采集范围必须可见 |
| 只记录电脑播放 | 所选 App 系统音频 | 不宣称麦克风仍在记录 |

预填不等于已经采集；只在用户明确开始或明确做输入检查时申请权限与采集。来源 App 消失不扩大成“采集所有 App”。场景变化不得静默修改用户已选隐私边界。

主区显示“尚未开始记录”；输入检查显示各路真实电平及“检测到输入”，不可用一个合成波形证明识别或落库成功。AI 未配置时明确“可先记录，之后整理”，不阻塞会议开始。

### 4.2 数据流与同意

在第一次使用及模型目的地变化时，说明三个独立事实：音频交给哪一项本地服务；转录/笔记是否发送给当前配置的模型服务；正文最终保存到本机知识库。`127.0.0.1` 入口也不证明后面的代理没有外发，因此只说明已知路径，不给无法验证的“绝不出网”保证。

提供简短可复制告知文本，提示用户遵守会议、组织和参与者的记录要求。产品内的勾选是用户确认已履行要求，不是自动取得所有参会者的法律授权；本方案不作特定法域法律判断。参考产品明确告知的做法，但不自动播放 TTS、不替用户发到会议聊天。[^R01]

默认不自动对外共享。可选“本次只记录、稍后手动整理”；用户明确开启的自动整理记为当前会议策略，在结束时沿用同一模型目的地和隐私选择，不能因为设置后来改变就自动发向新端点。

### 4.3 会中 UI

正文占主区；右侧会议信息和说话人说明按需收起；底部“私密问答/我的笔记”默认折叠。只有一处主状态，避免同时写“正在记录”“已暂停”“麦克风可用”互相矛盾。

状态分为：采集状态、识别状态、保存状态。必要时显示“正在识别 · 已保存到第 N 段”；不要把“听到声音”渲染成“已经保存”。磁盘写失败时保留有界待恢复文本并给复制/重试出口，不继续显示绿色“记录安全”。

连续文本采用 sticky-to-bottom：用户处于底部才随新增 final 或 partial 跟随；主动向上滚动、选中文字或查找时固定视口，出现“回到最新”轻量入口。说话人归属修订更新 chip，不新增一份正文，也不抢焦点。

### 4.4 三种停止相关动作

| 操作 | 推荐语义 | 记录要求 |
|---|---|---|
| 静音麦克风 | 只停止本地麦克风一路上行；所选系统声音可继续 | 记录 mute 起止及来源；不假称释放了设备 |
| 暂停记录 | 停止所有选中来源进入会议转录；处理好暂停前已准入内容 | 停记区间显式；恢复后建立新的输入窗口，不能拼接成连续讲话 |
| 结束会议 | 不再准入新内容，完成有界收尾并封存 | 用户明确确认；保存成功与否由 Store 结果决定 |

暂停和恢复要在输入队列上有可测试的顺序，不只翻一个布尔值。保留“暂停前已接受的最后一句”与丢弃“暂停期间不应记录的内容”的界限；不允许将暂停前后音频拼成一个语句。

### 4.5 中断与复原

用户看到的是“哪些来源断了、哪段没有记录、下一步是什么”。设备拔出、服务断开、睡眠与所选 App 退出分别处理。自动重试仅在既定来源范围内、符合先前授权的重连策略下进行；睡眠醒来不静默开始新的录制。

重连以同一会议 ID + 新连接 generation 建立；所有 item 去重与归属键包含连接身份，旧回调不能写新窗口。来源恢复失败时不能无条件宣称“已恢复”，更不能在纯系统音频会议中显示“麦克风还在记”。

### 4.6 音频与转录质量的边界

混合来源必须保留真实来源类型与连续输入时间轴；系统音频与麦克风可能重复收进同一段外放，不能在转录层看到相似句就直接删除“重复”，因为真实会议也会重述决定。先用带授权的实际设备组合评估重复拾音、双讲、长静音、说话人重叠和语种混合，再决定采集/去回声策略；不因助手模块启用了某项音频处理就默认会议链也已经验证。

业务词、缩写和人名提示只影响识别输入，不静默重写原始 final。会后识别修正形成可追溯 revision。分人结果是本场匿名标签，不等于人员身份；重连后的标签若无可靠连续身份，明确使用新连接的标签命名空间，人工映射后才合并。

音频缓冲溢出、采集格式转换失败、网络队列背压和 ASR 空终态分别计数；未保存 PCM 的情况下，丢掉的采集不能事后重跑。必须把这项不可恢复边界带入来源覆盖与纪要说明，而不是让用户看到一份完整流畅的假全量纪要。

## 5. 结束会议：先形成可信来源，再交给 AI

### 5.1 推荐收尾状态机

```text
Recording
  → StopRequested（同步停止接纳新输入，锁定本次会议 ID）
  → InputClosing（停止采集并记录已接受样本水位）
  → TransportFinalizing（等待本次关联终态和输入完成回执）
  → ApplyingFinalEvents（允许尾句/辅助事件更新原会议；不接受新录制）
  → PersistenceFlushing（等待该水位对应的应用层写入全部完成）
  → SourceSealing（持久化来源快照、缺口与封存结果）
  → Archived（释放本次设备/连接，会议文档保持可访问）
  → MinutesQueued（仅当用户选择了相应整理策略）
```

顺序允许提前释放物理设备，但不能因为设备已停就宣布所有文字已保存。传输 ACK 只证明服务处理进度，不证明下游 UI 或数据库消费完成。处理终态的接收循环不得等待一个只有它自己才能消费的后续事件。

### 5.2 两道屏障与错误结果

第一道是协议完成屏障，以当前契约的关联 ID 和累计输入样本水位为准；第二道是应用保存屏障，以本次会议已接收事件序列/行写入结果为准。若现有事件适配没有暴露足够标识，应在调用方内部补齐，不编造服务端字段。[^C11]

只有两道屏障均完成，才可显示“文字记录已完整保存”。允许明确降级封存：例如“正文已保存；最后一段归属未完成”，或者“最后一句未能确认，已保留待恢复片段”。降级快照必须携带覆盖与缺口信息，纪要页可见，不能用默认 00:00、空说话人和绿色完成掩盖。

### 5.3 来源快照的输入

来源快照包括本次 final 行及其版本、说话人显示名映射版本、用户选择加入的笔记版本、终态水位、采集/识别中断区间、文本未确认情况以及时间证据质量。所有组成在同一一致性边界读取或按 immutable revision 集合冻结。

保存 snapshot 后再排纪要任务。正常完成、用户重复点击结束、菜单结束、切换会话触发结束、重启恢复都使用同一幂等收口。纪要服务失败不能回滚来源；封存失败不能靠“AI 能生成出一段文字”冒充记录已保存。

## 6. 纪要生成：从一段 Markdown 升级为有证据的文档

### 6.1 用户看到的结构

默认纪要依次为：简短概览、主要讨论、明确决定、后续行动、尚未达成结论的事项。没有决定就明确“本次未记录到明确决定”，不要为了填满模板创造决定。风险/分歧只在有内容时出现；实现详情与模型信息放入“生成详情”。

每条重要结论有“查看依据”。选择后在右侧打开具体原文与相邻上下文；窄窗口使用可返回的详情面，不挤毁正文。普通段落不必挂几十个引用标记；可以按句子或条目合并显示来源数量，但底层仍保留具体对应。

### 6.2 生成流程

```text
已封存来源快照
  → 校验输入与数据流策略
  → 计算模型上下文/输出预算
  → 按主题和发言边界形成有界窗口
  → 逐窗提取事实候选、决定候选、行动候选与来源定位
  → 全局去重、处理修正/撤回/分歧
  → 回到原文补齐关键证据
  → 结构校验 + 引用校验 + 数值/实体/否定约束检查
  → 原子保存待核对候选
  → 用户核对并选择采用
```

短会可用一个窗口，但必须走相同验证器。长会不能只取开头或末尾，也不能因为 provider 接受了长请求就推断模型充分覆盖了整场。

### 6.3 长会议的预算和覆盖

按实际 provider/model 的上下文能力与 tokenizer 预算选择窗口，保留提示、输出和安全余量。缺少 tokenizer 时使用保守估计并在超限时继续拆窗，不使用字符数冒充 token。可从每窗约 2,500～4,000 token 的实验配置开始，但这不是当前模型能力承诺，实施时必须按目标模型校准。

分窗优先完整话题/发言轮次。重叠只用于理解上下文：每个来源单元有唯一 owned 区间，邻窗只读重叠内容，合并以来源身份去重，避免行动项重复创建。超长单句必须明确切分与范围映射。

保存覆盖 manifest：所有 eligible final 来源单元的 owned 覆盖、已处理窗口、失败窗口、缺口、输出截断情况。没有被处理的窗口不能消失在“100%完成”里。失败窗口可局部重试；候选可以部分可用，但不得标“整场完整”。

不同于简单“摘要的摘要”，全局合并必须能访问候选对应原文。决定的提出与撤回相隔很多窗口时，保留两个事件；最后的确立依据不足时写“存在分歧/未确认”，不能自动选最新一句。

### 6.4 事实保真与结构约束

以下是程序侧必须约束、模型提示只能辅助的内容：来源 ID 属于本次快照；引用原文在指定 revision 中存在；数值、单位、否定、条件、负责人和期限没有被无依据转换；重复来源不会生成重复行动项；输出大小、条目数、层级和字符串长度有界。

JSON 合法不代表内容真实。schema 错、空输出、refusal、incomplete/截断要分别报告。纯文本结果可保留为“未结构化候选”，供用户阅读/复制，但不能创建已通过结构验证的决策/行动数据，也不替换当前采用版。[^R17]

负责人未明记为 null/“待明确”；“我们看看”“建议研究”是建议，不是承诺；“若评审通过，下周上线”必须保留条件。日期保存原话和解析值，会议时区明确且语义无歧义时才解析“下周五”；不能按生成当天猜日期。

### 6.5 审阅不应成为繁重的标注工作

默认完整可读稿，主动作“采用这版”，次动作“修改”；关键疑点聚合成少量可定位事项：数字变化、负责人不明、时间歧义、结论与原文不一致、来源缺口。不要逐句要求打勾。

允许用户直接修改纪要，自动保存编辑草稿，支持撤销/重做。修改有证据关联的句子后要重新检查依据；用户新增的事实若没有转录来源，标为“用户补充”，不从邻句继承引用。采用后的徽标为“已由你核对”，而不是“所有参会者已确认”。

### 6.6 三个不同的版本指针

`latest_attempt` 表示最近整理尝试；`latest_successful_draft` 表示最近通过基本校验的候选；`accepted_revision` 表示用户当前采用版。它们不能合成一个 `is_latest`。

已采用 v2 后生成 v3，即使 v3失败或停止，打开知识库默认仍看到 v2，旁边说明“新整理未完成”。用户查看 v1 时，复制、导出、引用都固定 v1；换模型重新生成不改 v1/v2。对旧版进行修订产生子版本，不原位覆盖旧版。

## 7. 持久知识库：数据模型、来源与版本的工程契约

### 7.1 四层结构与单一权威

```text
采集/Realtime 层
  MeetingSession → 只负责本次采集、事件归属、收尾
                  ↓
权威知识层（现有 SessionStore 管理同一个业务数据库）
  原始转录与校订版本 → 来源快照 → 纪要版本 → 决策/行动项/修订事件
                  ↓
派生层
  搜索分块 → FTS → 可选 embedding / 重排 → 临时答案缓存
                  ↓
呈现与使用层
  当前会议 / 纪要核对 / 会议知识库 / 来源查看 / 跨会议问答 / 导出
```

不建立另一套会“反向覆盖”原稿的 Agent 长期记忆。知识服务可作为现有 Store 的门面，按文件拆分 SQL 和领域操作，但不要为每个业务表创建一条彼此不协调的写连接。

本方案中的新类型/文件名均为建议名，不代表当前仓库已经存在。可以先在既有文件中形成明确接口，随工作包渐进拆分，不做大爆炸重构。

### 7.2 建议核心对象

| 对象 | 最小关键字段 | 规则 |
|---|---|---|
| `MeetingDocument` | documentID、可选 sourceSessionID、title、projectID、occurredAt、timezone、visibility、deletedAt | 独立于活动会话对象存在；导入文档可没有采集会话；不伪造“录过音” |
| `TranscriptRevision` | revisionID、lineID/sourceUnitID、text、origin、parentRevisionID、editedAt | ASR 原文和用户修订分开；新修改产生新 revision |
| `MeetingSourceSnapshot` | snapshotID、documentID、ordered revision refs、speakerMapRevision、notes refs、coverage、seal result | 生成基于固定快照；同一任务不能边读边跟随变化 |
| `MinutesRevision` | revisionID、documentID、parentRevisionID、snapshotID、structuredBody、renderVersion、reviewState、createdBy | 生成、人工编辑、导入是不同来源；历史不原地覆盖 |
| `EvidenceAnchor` | anchorID、snapshotID、sourceRevisionID、范围/完整单元标识、quote、verification、timingQuality | 范围和 quote 由程序校验/提取；不是模型随便提供一个可点击链接 |
| `KnowledgeItem` | itemID、documentID、type、originRevisionID、currentEditRevision、evidence refs | 决定/行动/风险/未决问题有稳定身份，不按文本哈希当唯一业务 ID |
| `KnowledgeItemEvent` | eventID、itemID、kind、effectiveAt、recordedAt、actor、reason、evidence refs | 完成、取消、撤回、替代与人工更改留历史 |
| `MinutesJob` | jobID、documentID、snapshotID、configSnapshot、status、attempt、leaseOwner、fence、remoteID | 任务尝试不是内容版本；恢复认领原任务 |
| `IndexManifest` | indexGeneration、documentRevision、tokenizerVersion、optional embedding identity、state | 仅派生；可重建；旧索引不能让删除/撤回内容复活 |

第一期可以只落地文档、来源快照、纪要版本、引用和任务表；行动项事件与语义索引随依赖到位再加。不要一开始实现通用本体、复杂实体图谱或所有业务对象的全量 event sourcing。

### 7.3 与现有表的衔接

保留现有 `session/line/speaker_name/minutes/inner_os_*` 用户数据。新增 `meeting_document` 及 revision/evidence/job 扩展表，或在明确迁移中扩展现有 minutes；具体表名可调整，但必须保持上述语义。

推荐原生会议初次归档时建立 document 与 session 的唯一映射；知识文档不依赖 `MeetingSession` 的内存寿命。文档标题/项目元数据由知识文档持有；仍需供旧会话列表显示的标题，在同一事务同步或通过统一查询投影读取，不能出现两个独立可改、互相漂移的标题源。

普通 `removeSession` 遇到已关联的会议文档，应要求使用知识域删除入口；用外键 RESTRICT 或等价数据库约束阻止旧调用悄悄级联销毁知识。导入会议文档允许 sourceSessionID 为 nil；删除/脱离关联必须经过明确领域操作，不由运行时清理自动触发。

### 7.4 来源锚定：先整段可靠，再做精确片段

第一期让模型引用程序分配的 `source_unit_id`，每个单元映射到一条或一组固定行 revision。程序生成整段引文和相邻上下文，避免让模型猜字符偏移。

需要更细引用时，模型可以提出 quote，由程序在指定 revision 中匹配；精确出现一次才记录范围，多次出现要求补充上下文或退回整段，不猜第一个。Swift 视图使用 UTF-16 范围时必须显式转换和边界校验；不能把 Unicode scalar、Character 和 UTF-16 偏移混用。

引用结构可采用以下形状，真实 ID/hash 由程序生成：

```json
{
  "anchor_id": "anchor-demo-1",
  "snapshot_id": "snapshot-demo-1",
  "source_revision_id": "line-revision-demo-27",
  "range_kind": "whole_unit",
  "quote": "先完成灰度验证，再决定是否全量发布。",
  "verification": "exact_source_match",
  "timing": {
    "quality": "unavailable",
    "start_seconds": null,
    "end_seconds": null
  }
}
```

这是**格式示例，不是真实会议内容**。`exact_source_match` 只证明引文确实来自该来源，不证明纪要陈述被引文充分支持，更不证明 ASR 没听错。

### 7.5 结构化纪要契约示例

程序持有 document/snapshot/schema/prompt/template 版本；模型只生成受约束候选与来源单元引用，不允许模型自行写入用户审阅状态、数据库主键或“已完成行动”。

```json
{
  "schema_version": "speechrail.minutes.v2",
  "title": "发布评审",
  "overview": [
    {"text": "讨论了灰度验证及发布条件。", "source_unit_ids": ["u17", "u18"]}
  ],
  "decisions": [
    {
      "local_id": "d1",
      "text": "完成灰度验证后再决定是否全量发布。",
      "modality": "conditional",
      "conditions": ["完成灰度验证"],
      "source_unit_ids": ["u18"]
    }
  ],
  "actions": [
    {
      "local_id": "a1",
      "task": "补充灰度验证结果",
      "owner_text": null,
      "due_expression": null,
      "source_unit_ids": ["u17"],
      "commitment": "proposed"
    }
  ],
  "open_questions": [
    {"text": "全量发布的具体时间尚未确定。", "source_unit_ids": ["u18"]}
  ]
}
```

保存时程序分配稳定 itemID、生成 evidence anchors、关联固定快照、写入审阅状态。owner 的显示名不直接变成人员账号，匿名“一号”不跨会话当作同一个人。导出允许显示“未明确负责人/期限”；不能为了 JSON 完整性让模型填“待定”后再自动解析成具体时间。

### 7.6 原子提交与防旧结果覆盖

关键操作必须是领域事务，而不是 UI 连续调用多个独立写接口：

- `sealMeetingSource`：写封存结果、来源快照和文档关联，失败全部回滚。
- `enqueueMinutesJob`：写固定快照任务和 latest_attempt，原已采用版不变。
- `saveMinutesCandidate`：校验 job fence、来源身份、结果结构后写 revision/evidence，再更新 latest_successful_draft。
- `acceptMinutesRevision(expectedAcceptedRevisionID:)`：比较用户开始操作时的采用版本，冲突则要求刷新；写审阅记录与当前指针。
- `finishPrivateExchange`：校验 exchange/session/task generation，以 UPDATE 收尾并在同一事务保存证据；失败 UI 不显示已保存。
- `deleteMeetingKnowledge`：先写不可检索的删除状态，立即阻断使用，再按精确范围清理派生和实体。

索引任务采用事务 outbox：业务修订与“需重建索引”的记录一起提交；索引失败只影响新内容的检索更新，不回滚用户内容。呈现应允许看到“已保存，索引更新中”。

### 7.7 生命周期不变量

1. 新版生成失败不影响旧版可读、可导出、可被明确引用。
2. 来源修订后，旧纪要与引用仍可作为历史查看，但不自动冒充新事实。
3. 只有明确采用动作提升当前采用版；重试、重启、索引更新不得提升。
4. 任何旧异步任务在 await 之后，重新校验 documentID、snapshotID、request generation 或 fence。
5. 跨会议问答结果不能被自动写回成其自身来源；用户保存答案时必须保留派生关系，避免自证循环。
6. 整场导出、当前版本导出和单条引用必须是不同且准确命名的选择。
7. 业务上的不可变版本不阻止用户完整删除个人数据；删除后不得靠快照或引用暗中保留全文。

## 8. 纪要任务：可恢复、可取消，而不是一直转圈

### 8.1 任务和版本分离

一个生成意图绑定一个 `jobID + snapshotID + configSnapshot`；该任务可以重试多次，但只有成功候选产生内容 revision。用户主动“重新生成”才新建生成意图；恢复过期租约不新建会议、任务意图或无意义的版本号。

任务状态建议：`queued / running / waiting_remote / cancelling / cancelled / succeeded / failed / blocked_configuration / stale_source`。UI 将其翻译为普通语言，不把 lease/fence/response_id 展示在主界面。

### 8.2 执行者所有权

认领在事务中完成，对 jobID 和预期状态作条件 UPDATE，递增 fence；每次 heartbeat、保存进度和终态提交都带 owner + fence。旧执行者即便迟到成功也不能覆盖新执行者。仅“单个 actor”不足以替代异步任务的逻辑所有权。

执行者崩溃后，下一次启动扫描原任务：本地任务从已持久化的窗口进度继续；远端任务存在持久 response ID 时先查询原请求；远端不可恢复或已过期时才报告并由重试策略建立新 attempt。不能见到 running 就把整场再发一遍。

### 8.3 模型能力与隐私

分别识别文本生成、结构化输出、异步后台请求、查询与取消能力。兼容 OpenAI 的端点不能自动视为支持全部 Responses 扩展。若后台能力不可用，可使用受 App 管理的普通请求执行同一持久任务；不静默改为未经确认的新云供应商。

本地模型/远端模型都要冻结本次配置与策略。密钥仅在调用时按安全来源解析，不把 API key 放进 job；变更端点、模型或隐私模式后，应显示“新配置从下一次任务生效”或请求明确迁移当前任务。

OpenAI 官方 background 文档说明异步执行和轮询会涉及临时 response 存储。因此 UI 不能把“保存在本机”或一个 `store=false` 字段，扩写成所有 provider 下都不存在远端留存。以实际端点和组织策略判断；保存内容归属与传输目的地分别说明。[^R16]

### 8.4 取消、重试与失败

停止整理只取消指定 job，不终止另一场正在记录的会议，也不删除已存来源与旧纪要。若 provider 支持远端取消，应发送并等待有界确认；超时显示“本地已停止接收，远端取消未确认”，不谎称云端任务已消失。

429/临时网络错误可在有界预算内退避重试；认证、输入超限、schema不支持、证据失败不能无限重试。每个失败有原因和有效出口：去配置、重试失败片段、查看已保留候选、导出原文。停止后的 late response 只允许写任务诊断，不得自动采用或覆盖用户编辑。

### 8.5 远端提交结果未知时，不承诺“恰好一次”

请求可能已被供应商接受，但 App 在收到或持久化 responseID 前断开。若供应商没有可验证的幂等请求能力，单靠本地 jobID 无法保证远端恰好执行一次。此时任务必须进入“远端提交结果未知”，先查询可用回执；无法查明时说明重试可能重新执行/计费，由明确策略或用户选择决定，不将网络超时一律自动重发。

本地候选发布仍可用 jobID + fence + 唯一约束保证不重复；这与远端推理是否重复是两个不同的保证。日志只记脱敏请求身份和状态，不记录正文补偿诊断。

## 9. 从纪要到长期知识：决策、行动项、跨会议变化

### 9.1 自动入库，但不自动“确认事实”

转录封存后会议文档就出现在库里；AI 候选落盘后显示“已保存 · 待核对”。即使用户从不按“采用”，仍能查到并导出这些材料。用户核对决定默认采用版及知识状态，不决定内容是否存在。

默认搜索返回当前采用版；没有采用版时返回最近可用待核对稿，并醒目标识。原始转录保持可搜索。严格问答可选择“只使用已核对纪要”；普通问答使用待核对材料时必须逐项说明，不隐藏所有未核对会议导致用户误以为丢了资料。

### 9.2 行动项有两个不同的状态维度

**内容状态**说明原会议是否明确提出/承诺、是否经用户核对；**执行状态**说明后来是否完成、取消或被替代。不能把“我确认这条纪要写得对”自动改成“行动已完成”。

建议执行状态为未开始、进行中、已完成、已取消，并保留每次变化的时间、操作者和来源。由于负责人不一定是本 App 用户，不自动发提醒或外部任务；这些属于单独授权的集成能力。

第一次生成可自动列出候选；真正进入用户工作清单需要可逆的确认操作。再生成只提出变化 diff，不能把已完成项重新打开、复制成另一条待办或重置负责人。以稳定 itemID +来源关系保留用户改动，不仅按文本相似度合并。

### 9.3 决策的历史与现状分开

存 `effectiveAt`（事情何时生效，未知则空）与 `recordedAt`（何时记入库）。决定可能“提出—暂缓—确认—修订—撤销”；以显式关联记录替代关系，默认不因后一场会议日期更晚就替代前一场全部决定。

同名项目、相似句子和相反结论不能自动合并。明确跨会议冲突时，答案同时给出两处来源，要求用户确认适用范围；不让模型用语气更肯定的一段压过另一段。

### 9.4 场景示例：两个月后追溯发布决定

以下为虚构验收材料：9 月某场会议说“达到灰度门槛后上线”；10 月另一场说“等待安全复核，原计划暂缓”。用户问“为什么还没上线？”

正确结果应同时显示最初条件与后续暂缓理由，指出谁在何次会议中提出、哪些信息未明确。它不能只返回旧纪要中的“上线”，也不能把10月的“暂缓”说成永远取消。若第二场只出现个人建议而非决定，应明确这是建议，不是已生效变更。

### 9.5 与语音助手的关系

会议知识不等于 `assistant_memory`。后者是用户明确确认的偏好/长期记忆；前者包含完整项目历史和多方观点。不得将全部纪要自动拼入语音助手的 developer prompt。

语音助手未来使用知识时，通过只读 `MeetingKnowledgeService`，携带用户选定的项目/会议范围、可信级别和时间范围检索。语音回答简短，屏幕上保留引用；发出模型请求前校验目的地权限，不把本地保密文档因为“助手可以聊天”就发到另一家云端。

## 10. 本地检索与跨会议问答

### 10.1 检索分三条路

| 用户意图 | 查询路径 | 不应采用 |
|---|---|---|
| 查关键词、人物、产品、版本号 | 词法全文检索 + 精确字段 + 筛选 | 只依赖语义相似度，丢掉数字和专名 |
| 列出全部未完成事项、按项目计数 | 结构化关系查询、完整分页 | 用 top-k RAG 结果冒充“全部” |
| 问原因、关联、演进 | 检索相关原文/纪要/变更事件后有证据回答 | 把所有会议堆进一个超长 prompt，或者只检索当前摘要 |

第一期搜索范围含标题、项目、采用/待核对纪要、转录、决策与行动项；私密问答默认不参与普通会议检索。当前表中已有数据要纳入迁移和重建，不要求用户重新生成所有旧纪要才可搜索。

### 10.2 中文全文检索的最低要求

采用 FTS5 前检查目标 App 使用的 SQLite 编译能力；编译可用不是中文分词正确。固定 tokenizer 方案与版本，并对文档和查询使用相同规范化。

首期可采用受控中文词切分与有限二字候选策略，保留英文整词、数字、小数、产品名、版本号和大小写折叠。缩写别名由程序词表或用户确认，不把短缩写扩成任意领域名词。

FTS5 trigram 的全文 MATCH 对不足三个 Unicode 字符的查询存在限制；“预算”“回滚”等两字查询不能只走 trigram。需要明确的短词通路，例如已建的词项/二字索引，或在受范围/结果数限制的原文 LIKE 上回退，并标记该检索策略。BM25 排序方向和分词效果均用固定样例验证。[^R10]

排序优先相关性，辅以项目/时间筛选；新近不总是更正确。相同会议的重复版本不占满前 N 条，默认按当前使用版本去重；历史版本搜索是显式开关。

### 10.3 可选的语义检索与融合

只有概念性查询的召回仍明显不足，且用户批准相关模型使用后，才加入 embedding。接口记录模型 ID、revision、维度、归一化规则、分块版本；换模型需新建索引 generation，不把不同维度/向量空间混查。

先在同一可见范围内分别得到词法和语义排名，再用 RRF 等排名融合方式合并；可选小规模 reranker。参数由本机语料确定，不能复制云服务排行榜或供应商提升百分比当本机收益。[^R11]

分块附带确定性上下文：会议标题、日期、项目、主题、内容状态及来源 ID。Anthropic 的 Contextual Retrieval 展示了为片段补充上下文并结合关键词/向量检索的方向；本项目先用数据库已有元信息，不为每个片段额外生成一段可能捏造的“背景”。[^R12]

### 10.4 查询的安全与时效流程

```text
用户问题 + 显式范围
  → 解析检索意图（事实、统计、跨会演进）
  → 过滤文档范围/删除状态/私密性/采用版本
  → 召回 + 去重 + 原文补全
  → 固定 RetrievalSnapshot（文档 revision 与检索版本）
  → 按证据生成回答（不拥有执行工具权限）
  → 校验引用与关键陈述
  → 再检查删除/权限/版本是否改变
  → 呈现答案、来源与不足
```

结构化查询必须由受约束代码构造参数，不执行模型给出的任意 SQL。检索结果中的“忽略前文”“发送邮件”“泄露其他会议”等内容只是会议文字，不是应用指令。RAG 不能天然解决提示注入，所以资料和执行权限必须分层。[^R18]

### 10.5 答案呈现契约

答案以结论开头，按条关联证据，注明截至哪次会议或哪版资料。遇到无足够证据、只覆盖部分会议、来源相互冲突或仅有未核对稿，应直接说明；不要输出模型自报的“92%置信度”。

“没有找到记录”不等于“这件事从未发生”；“某人未在转录出现”不等于“没有参加”；“检索到的十项都已完成”不等于“全部项目任务已完成”。系统需要展示检索范围和筛选口径，复杂数目类问题由完整结构化查询回答。

用户保存问答结果时，新建有来源的派生笔记，附原问题、检索快照和使用版本；不将生成答案重新索引为与原始会议同级的权威。源文撤回/删除/修订后，该笔记和答案缓存应显示受影响状态。

## 11. 私密问答、用户笔记与知识边界

### 11.1 先修复真正的保存

`InnerOSSession` 的问答是用户资产，应使用“一次建行、状态化收尾”而不是多次普通 INSERT。生成请求分配 exchangeID 和 generation，先保存 generating；终态按同一 exchangeID/sessionID UPDATE，并在同一事务写入验证后的证据。受影响行数为 0 必须报错，不把不存在当成功。当前 Store schema 已证实 ID 为主键。[^C05][^C06][^C08]

切换或解绑会议时，撤销该次问答写入 UI 的权利；可按用户选择保存旧问答到其原会议，但不能展示在新会议下。旧任务的 defer 不能清除新任务句柄。读取失败不能用空数组伪装成“没有问过”，存储失败不能只更新屏幕。

### 11.2 “加入纪要”必须有真实路径与正确称呼

建议改为“加入纪要的补充说明”。点击后选择加入内容，保存其来源为 `user_selected_ai_note` 或 `user_note`，并进入新的 source snapshot。主纪要中的“会议决定”仍以会议转录证据为依据。

私密问答不能因用户选择加入其中一句，就整段问题、个人判断、其他证据和未选择内容一起外发或导出。用户撤回加入后，下一版快照排除它；旧版作为历史保留其当时状态，但分享和检索需遵循当前隐私控制。

### 11.3 知识库中的私密性不是一个装饰标签

默认公共会议检索范围不含私密问答和私人便签。用户可单独选择“含我的私人笔记”，该选择只影响当前查询/明确保存的偏好，不自动改变导出范围或其他模块权限。

源数据的隐私级别变化需要同时影响搜索、AI 上下文、引用面板、已保存派生笔记和导出预览。没有服务器多人协作时，不必先造完整 RBAC 系统，但本机可见范围、端点外发允许范围和分享选择必须真实执行。

## 12. 持久性、备份、迁移、导出与删除

### 12.1 什么才算持久

应用内“已保存”表示权威 Store 已完成对应事务，不表示 ASR partial 也已保存，更不表示所有断电、磁盘损坏或外部删除都不会造成损失。

现有 WAL + NORMAL 保证了一致性与普通应用崩溃下的事务保护，但 SQLite 官方明确区分断电/系统故障时的提交耐久性。建议对知识权威写入口使用经过验证的 FULL 策略，并实测 final 行写入及 UI 延迟；索引仍是可重建派生物。不要每个 token 强制一次磁盘提交，也不要为了快而不说明风险。[^C05][^R15]

记录原始 ASR final、纪要候选、用户编辑、采用版本、行动状态都走明确持久化确认。新增任意后台任务不得删除旧内容释放空间；磁盘不足时有可见失败和用户控制的导出/清理入口。

### 12.2 延用现有备份能力，补齐恢复产品

现有 `SessionStore.backup(to:)` 已经采用 `VACUUM INTO`。它是应延用的正确基础，不需要让用户去 Finder 只复制正在使用的主数据库文件。SQLite 官方也提供在线备份 API。[^C05][^R13][^R14]

完整流程建议：创建一致快照 → 校验可打开与 schema → 检查 `integrity_check`、外键、关键对象数量和引用关系 → 生成清单 → 原子发布到目标路径 → 记录最近一次成功备份。若 `VACUUM INTO` 导致较长业务阻塞，应安排在非录制期或评估增量备份连接，而不是在实时线程执行。

自动备份功能应由用户启用并选择目的地，默认不替用户创建云同步关系。应用内备份可以保留一份最近良好快照，但必须提醒同一块磁盘不能覆盖设备损坏风险。独立介质/目录的副本与可验证恢复是不同能力，不能将“已同步”当成“已备份”。

### 12.3 恢复不能覆盖正在使用的库

```text
选择备份 → 读取 manifest 和 schema → 在临时位置校验
  → 检查完整性/外键/文档版本/来源引用/删除状态
  → 展示将恢复的范围和备份时点
  → 停止相关写任务、关闭数据库连接
  → 为当前库生成回退快照
  → 切换到已验证的新库
  → 重新打开并抽查关键对象
  → 重建派生索引；保留回退点
```

损坏备份、未知 schema、新版库被旧版应用打开时不得自动清空重建。恢复失败保持原库；恢复期间不能继续在另一条连接写入待替换文件。完整恢复操作在实施/运维阶段需要用户明确授权，不因本文提及就执行。

### 12.4 开放格式与两种导出包

| 包类型 | 默认内容 | 用途与保护 |
|---|---|---|
| 分享包 | 用户选定纪要 revision、必要元数据；来源片段按选择加入 | 默认不含完整转录、私人问答、密钥或隐藏草稿；预览后导出 |
| 知识归档包 | 文档与全部选定版本、结构化 JSON、来源与修订映射、行动事件、manifest、可读 Markdown | 用于迁移/恢复/长期持有；私人内容需明确纳入，提示敏感性 |

建议目录（示例，不表示已实现）：

```text
SpeechRail-Knowledge-Export/
  manifest.json
  README.md
  documents/<document-id>/
    document.json
    minutes/<revision-id>.json
    minutes/<revision-id>.md
    sources/<snapshot-id>.json
    source-revisions.jsonl
    evidence.jsonl
    knowledge-items.jsonl
    item-events.jsonl
```

清单声明 schema/exporter 版本、导出时间、范围、采用版、来源是否完整、私密内容是否包含、文件大小与校验值。业务 ID 与实体引用在重导入后仍可解析；不导出 API key、环境配置、模型路径、日志、embedding 原始向量或未获授权的原始音频。

Markdown 用于离开应用后仍能阅读，结构化 JSON 用于保真迁移。外部编辑 Markdown 后重新导入，建立新版本/用户补充，不能以文件监视器静默回写权威库。原文不存在的导入文档标为“外部导入，未提供转录依据”，不伪造来源。

### 12.5 导入安全与重复处理

导入前检查文件数量、总大小、压缩膨胀比、相对路径、重复 ID、外键、枚举和字符串上限，拒绝目录穿越和符号链接越界。先暂存再事务提交，不半场入库后失败留下幽灵行动项。

同 ID 同内容可幂等跳过；同 ID 不同内容进入冲突预览或分配新导入身份并重写内部引用，不能覆盖用户现有采用版。导入文件中的链接默认不联网抓取；笔记文字与模型提示始终当作数据。

### 12.6 归档与删除要准确区分

“归档”只是整理状态，仍可搜索；“删除”改变可见性并影响依赖；“完整删除”包含本场所有修订、引文、问答、派生问答缓存和索引。默认不设置定期自动过期，除非用户明确配置保留策略或有适用的组织要求。

对“只删除完整转录、保留纪要”必须预览：是否保留引用所需的短片段、哪些结论以后不能回原文。只有用户明确选择，才可保留这些片段，并标识“完整转录已移除，保留的是引用片段”。不能一边说原文已删除，一边在 snapshot 中偷偷保留完整文本。

删除首先在权威库打不可使用标记，检索与生成前后都过滤；再按 job 清理派生索引、缓存和文件。旧 reindex/问答任务的迟到结果不能复活内容。完整删除后，引用链接应显示“来源已移除”，不能改指别的相似会议。

已导出的外部副本和离线备份不可能被本机删除按钮自动撤回，应明确告知。对由用户掌管的备份提供选择性销毁/重新生成流程；不偷偷扫描用户所有外部盘。备份恢复可能带回备份时点的历史数据，恢复预览必须说明这一点。

### 12.7 存储安全

本机 SQLite 不自动等于加密存储。沿用系统账户隔离、受控数据目录权限和钥匙串管理密钥；需要应用级加密或加密归档时单独引入明确方案与恢复密钥流程，不写“加个密码就安全”。

记录目录与 runtime/model/cache 清理范围严格隔离。导出先给内容范围预览；不将全文、私密问答或证据引文加入诊断日志。内容 hash 只能在私有业务存储中用于一致性核对，不作为可公开传播的隐私保护证明。

## 13. UI 交付规格：当前会议、纪要与知识库

### 13.1 信息架构

在“会议助手”内部建立两个清晰入口：**当前会议**和**会议知识库**。当前会议负责记录状态，知识库负责历史阅读、整理、检索和复用。不必立即改变整个 App 的14路由结构；可先使用模块内导航和明确深链接。

知识库不再依赖是否保留一个 archived `MeetingSession`。直接从冷启动搜索旧纪要，应该与“刚结束后点进去”看到同一文档组件。

### 13.2 三个核心页面

| 页面 | 主区 | 主要动作 | 次要/渐进披露 |
|---|---|---|---|
| 当前会议 | 转录、当前来源与真实状态 | 开始/结束，按状态给一次 | 输入设置、说话人、私密问答、标重点 |
| 会议文档 | 概览、讨论、决定、行动、未决、来源状态 | 修改/采用、查看来源 | 原文、版本、生成详情、导出、删除 |
| 会议知识库 | 搜索、项目/时间筛选、完整会议列表、结果摘要 | 搜索/打开 | 行动视图、决策变化、备份/导入、跨会议提问 |

文档详情可采用“纪要 / 文字记录 / 我的笔记”三个任务标签；版本选择独立但不常驻占大面积。当前版本、审阅状态和来源完整度简洁显示。内部 task/generation/fence 不变成普通用户要理解的概念。

### 13.3 状态文案契约

| 真实状态 | 建议文案 | 不能使用的替代说法 |
|---|---|---|
| 未开始、来源已选 | 尚未开始记录 | 正在聆听、说话即录 |
| final 正在等待保存 | 正在保存最近文字 | 全部记录已保存 |
| 部分来源中断 | 电脑声音中断，麦克风仍在记录（仅真实成立时） | 会议已正常恢复 |
| 文档已存、AI未整理 | 文字记录已保存，可稍后整理 | 会议失败 |
| AI候选已存 | 纪要已保存，待你核对 | 会议结论已确认 |
| 新版生成失败 | 新整理未完成，仍在使用第2版 | 最新纪要为空 |
| 编辑保存失败 | 修改尚未保存，内容仍在这里 | 已保存 |
| 索引更新失败 | 内容已保存，搜索索引待更新 | 内容不存在 |
| 引用无精确时间 | 第27段 · 发言时间未确认 | 00:00、精确回放 |
| 仅本地持久记录 | 记录保存在本机；AI处理使用当前配置服务 | 所有处理都只在本机（未经证实） |

### 13.4 行为与可访问性

复用 `SpeechRailDesignTokens`、共享字体/间距/颜色/控件和系统导航。不要因为新知识库就追加一套自绘玻璃面板或固定超宽卡片。正文列宽可读、窄窗口降为单栏，来源面板收起后引用入口仍可键盘到达。

正文可选择复制；搜索保留关键词和筛选；返回列表恢复滚动与选中项。流式更新不抢焦点，不在 VoiceOver 中逐 token播报；对“已保存”“录制中断”“纪要已完成”作合适的离散通知。颜色与 hover 不是唯一操作入口，尊重 Reduce Motion 和系统对比度设置。[^C12][^R19]

快捷键沿用应用菜单已定义的动作。新增查找与版本/来源动作先排查冲突；输入法组合文本、重命名弹层、删除确认占焦点时不得被全局“结束”或“采用”快捷键穿透。

### 13.5 所见即操作对象

详情读取返回单个 `MeetingReviewSnapshot`：文档、所选 revision、转录、说话人映射、引用与版本列表。请求捕获 selectionGeneration；返回时若选择已变，不得写回。

导出 API 必须带 `documentID + revisionID + scope`，不允许“当前正在看旧版，但函数默认取最新”。源版本不存在/已删除时返回明确错误；读库失败不能替换为空集合导出。

## 14. 工程落点与接口划分

### 14.1 现有模块的改造责任

| 现有位置 | 应承担的调整 | 不应增加的职责 |
|---|---|---|
| `MeetingSession.swift` | 身份与代际、输入事件、收尾屏障、当前会话恢复 | 不直接查询跨会议全文或生成知识问答 |
| `MinutesGenerator.swift` | 拆出有状态任务编排、生成与结果验证接口 | 不同时拥有唯一 UI、远端任务和最新内容指针 |
| `InnerOSSession.swift` | 幂等保存、代际隔离、证据验证、私密范围 | 不直接把模型判断并入会议事实 |
| `SessionStore.swift` | 增量迁移、原子领域写、来源/版本/知识查询、备份 | 不调用 LLM、播放音频或执行网络 |
| `SessionCoordinator.swift` | 保持设备所有权和兼容的持久化门面 | 不变成全文检索与所有知识状态的全局控制器 |
| `MeetingView.swift` | 当前会议与文档阅读复用、选择快照、操作范围 | 不在 body 拼SQL、推测保存成功或解析模型JSON |
| `SessionDomain.swift` / 导出相关文件 | 新结构、状态与导出契约 | 不将缺少证据填为虚构默认值 |
| `Package.swift` 与 Xcode project | 让相同生产模块进入可注入测试目标 | 不维护只在测试中生效的替代算法 |

新增建议名：`MeetingSessionDependencies`、`MeetingSourceSnapshot`、`MinutesJobCoordinator`、`MinutesEvidenceValidator`、`MeetingKnowledgeService`、`MeetingSearchIndex`、`MeetingKnowledgeQuery`、`MeetingKnowledgeLibraryView`。这些是可分阶段的责任边界，不要求每项都立即独立服务化。

### 14.2 关键接口形状（设计草图，不是可直接粘贴编译的实现）

```swift

func sealMeeting(
```

所有参数只表达必要领域身份，日志只输出允许的状态/计数，不打印整个请求和正文。函数签名不是新增公共 REST/MCP 契约的授权；先作为 App 内部接口实现。

### 14.3 与前两个模块方案的衔接

共享 `SessionCoordinator` 的结束/保存真实性、Realtime 屏障和身份隔离应与语音助手方案协同，不在会议助手分支维护另一套不兼容逻辑。提词器仍不建普通会话记录；知识库不能为了统一数据库强迫提词器保存语音或完整识别结果。

建立共享错误、引用范围、时间证据类型有价值，但不要把所有模块一次合并重构。每次共享变更必须补充对应助手、字幕、提词器的回归范围，保证会议改动不误停其他会话。

## 15. 22 个可执行工程工作包

工作包按用户价值和数据边界划分，不代表22个PR。P0为数据/控制安全与可信底座，P1为核心用户旅程和知识使用，P2为有条件增强。复杂度 S/M/L 是相对实施规模，不是未测量的工期承诺。每包应形成可独立评审的完整增量，但共享一个一致目标时持续追加到同一 Draft PR。

### MA-01｜会议生产编排可测试与身份门禁

**优先级/规模：** P0 / M。**代码落点：** MeetingSession.swift；新增 MeetingSessionDependencies；Package.swift / Xcode 工程。

**依赖：** 无；先读取目标作用域规则与已有测试清单。

**实施：** 将采集、Realtime、时钟和必要持久化结果通过窄接口注入，测试调用生产 MeetingSession。同步生成会议启动/连接 token；每次 await 返回重新验证。中止/重试只清理自身局部资源；发布到 self 前检查仍归当前任务。

**验收：** MC-01、MC-05～MC-08、MC-78；用可暂停 Gate 重现启动期间结束、两次重连与旧设备回调，不能依赖 sleep 碰运气。

**回退：** 接线仍使用原生产实现；回退不改变已保存内容，不删新建真实记录。

### MA-02｜item 级转录、时间证据与有界输入

**优先级/规模：** P0 / L。**代码落点：** MeetingSession.swift；Realtime 适配；SessionDomain.swift。

**依赖：** MA-01。

**实施：** 按 connection generation + itemID 管理 partial/final/failed 和去重，snapshot按revision替换。空final保留待恢复文本但不送正式纪要。分离observedAt与声学起止，修复时间质量只改标签而不验证值的路径。记录输入/队列丢失，不将receipt间隔当发言时间。

**验收：** MC-09～MC-16；重复final只存一次；未知时间显示未知；同ID跨连接不漏记；旧item失败不抹掉新partial。

**回退：** 可回退识别策略但不能丢弃用户恢复文本；新增时间字段缺省为空，不伪造旧数据精度。

### MA-03｜结束、尾句保存与来源封存屏障

**优先级/规模：** P0 / L。**代码落点：** MeetingSession.finishAndSummarize/releaseCapture；SessionCoordinator；Store。

**依赖：** MA-01、MA-02；与语音助手共享屏障改造协调。

**实施：** 将输入停止、协议完成、应用消费、持久化flush、封存结果显式分层。等待只在可消费相应事件的任务外发生。重复结束幂等；保存失败保留恢复上下文；快照冻结成功后才排纪要。显式返回成功/降级/失败，不用try?统一写成功。

**验收：** MC-17～MC-24；尾句写入被Gate阻塞时不提前发布归档成功；不得误停其他会话。

**回退：** 停止新纪要排队，保留已经保存的来源；受损尾部标为不完整，不假称恢复了音频。

### MA-04｜私密问答真实落盘与引用真实性

**优先级/规模：** P0 / M。**代码落点：** InnerOSSession.swift；SessionStore.inner_os_*；协调器门面。

**依赖：** MA-01；来源锚升级接 MA-05/MA-08。

**实施：** 创建一次exchange，终态条件UPDATE；答案、状态、证据事务写入。去掉同ID重复INSERT及吞错成功；切会撤销旧UI写权。校验quote与来源，不存在时标未验证。加入纪要改为显式补充说明并真正进入快照输入。

**验收：** MC-41～MC-45；关闭重开答案仍在；无效引文不发布；私密内容不进入普通检索/分享。

**回退：** 保护现有问答行；旧generating行按真实情况标为未完成，不能编造丢失答案。

### MA-05｜来源修订与知识文档增量迁移

**优先级/规模：** P0 / L。**代码落点：** SessionStore迁移；新增MeetingDocument/TranscriptRevision/SourceSnapshot。

**依赖：** MA-03；在正式迁移前使用 MA-20 的既有库备份。

**实施：** 建立文档与采集会话映射、不可变来源revision及快照。人工改文/标注名字不改原始记录。迁移现有纪要正文和版本，旧内容保留legacy标识；没有来源时不补造引用。数据库约束阻止旧removeSession入口无意级联删除知识。

**验收：** MC-20、MC-46、MC-67～MC-69；真实结构旧库样本迁移后正文/版本/ID关联可核对；迁移失败回滚。

**回退：** 只用迁移前验证备份恢复，不直接让旧程序打开不认识的新schema；明确新写入保留办法。

### MA-06｜纪要版本与当前采用指针原子化

**优先级/规模：** P0 / M。**代码落点：** SessionStore.enqueueMinutes/latest查询；Minutes域模型。

**依赖：** MA-05。

**实施：** 将任务状态与内容审阅分开；原子维护latest_attempt、latest_successful_draft、accepted_revision。生成失败不清旧指针；采用使用预期版本比较；手工编辑与生成是不同revision来源。所有查询返回明确选定版本。

**验收：** MC-25、MC-26、MC-31、MC-47、MC-48；新尝试插入失败/并发采用均不破坏旧版；所见版本可稳定导出。

**回退：** 旧版渲染可保留，新指针数据不可重算成“version最大就是采用版”。

### MA-07｜持久生成队列、恢复、取消与fencing

**优先级/规模：** P0 / L。**代码落点：** MinutesGenerator.swift；新增MinutesJobCoordinator；Store任务表。

**依赖：** MA-05、MA-06。

**实施：** 任务绑定源快照及模型配置，认领/心跳/完成带owner和fence。持久responseID及窗口进度；恢复原job不调用新建版本。探测background/poll/cancel能力；不支持时明确使用受管普通请求。取消指定任务，不影响录制或旧纪要。

**验收：** MC-27～MC-32；旧执行者迟到、远端任务已过期、App退出恢复、取消未确认均有确定状态。

**回退：** 可暂停调度而保留队列；不能以清任务表/删除候选作为回退。

### MA-08｜结构化纪要与证据、事实保真验证器

**优先级/规模：** P0 / L。**代码落点：** MinutesDocument/MinutesGenerator；新增MinutesEvidenceValidator。

**依赖：** MA-05、MA-06。

**实施：** 定义V2候选schema和来源单元ID；程序分配持久ID和引用。区分refusal/empty/incomplete/schema失败，禁止原文兜底后ready。验证引文归属、数字单位否定条件、未知负责人期限与建议/承诺类型；错误结果保留但不升可信。

**验收：** MC-33～MC-38、MC-46；schema合法但语义错误必须进入复核；不能把引文存在视作支持结论。

**回退：** 旧Markdown继续可读；停止新结构化发布而不是删除旧纪要。

### MA-09｜长会议分窗、覆盖账本和局部重试

## 16. 实施节奏与最小有用交付

### 16.1 里程碑

| M1：第一版持久会议知识库 | 来源版本、可核对纪要、当前采用版、历史文档、关键词查找、选定版本导出和恢复 | MA-05～08、MA-10～12、MA-15词法、MA-18～21 | 即使不开AI问答/向量检索，用户已能把会议当长期资料用；旧数据迁移与恢复验证通过 |

MA-20先提供既有schema备份，MA-05才执行实际迁移；迁移后再扩展MA-20的引用完整性和恢复用例。MA-22贯穿，不是所有功能写完才开始验收。以上不是严格串行瀑布：UI壳层与数据契约可并行，但未经数据门禁不得提前宣称知识保存可靠。

### 16.2 PR组织和并行冲突

用户批准实施后，先重新固定repo/base/SHA并对本方案查重；仓库已有修复优先复用，不把旧SHA上的发现不加核实再报新Issue。

建议按一致目标组织增量：会议收尾可靠性、纪要版本与任务、证据化纪要、持久知识库体验、跨会检索复用。每组首个完整且已验证增量尽早开Draft PR；同一目标后续以atomic commits追加，不机械做22个PR。

`SessionStore.swift`、`SessionCoordinator.swift`、`Package.swift`、Xcode project、共享Realtime契约是高冲突区域。先定义接口和分工，同一文件编辑串行；临时worktree隔离，不能用整文件还原覆盖用户或其他模块改动。

按仓库规则执行定向检查；日常push只轻量核对远端head，里程碑和merge-ready才审完整diff、测试与checks。未经明确要求不提交/推送/合并，不将“无checks”写成“CI通过”。本次只有方案文件，不产生这些远端变更。[^C02]

### 16.3 “不做也不影响第一版”的项目

向量检索、自动实体关系图、日历接入、外部任务双向同步、多人在线编辑、会议录音归档、桌面语音唤醒都不应成为M1依赖。模板市场、花哨仪表盘、给所有字段计算AI置信度也不是首要价值。

可以先提供通用纪要模板，额外内置“项目例会/方案评审/访谈”少量模板；模板只改变信息组织，不改变事实、引用和权限要求。不要把模板选择做成每次必须完成的前置步骤。

## 18. 质量、性能、耐久性指标与评估方法

### 18.1 先建立可重复基线，再约定发布目标

指标必须记录：代码SHA、App/服务版本、模型及revision、provider模式、模板/prompt/schema版本、分词和索引版本、硬件/设备、样本类别和数量。用户的真实会议、音频与原始问答不放仓库；提交可复现的虚构/脱敏fixture和聚合结果。

测试集至少包含：中文项目例会、技术评审、访谈；中英混语；产品名/编号/金额密集；长静音与插话重叠；提出又撤回的决定；含多个条件的承诺；无明确决定的会议；分窗首中尾都有重点；跨会议结论变更；不同项目同名人物/术语；私密问答与恶意指令文本；没有匹配资料的查询。

QMSum、MeetingBank 和 ExplainMeetSum 可用于方法和公开场景基线，但它们不替代目标中文音频、设备和用户内容分布的实测。ALCE 的思路可用于将答案正确性与引文质量分开验收。[^R05][^R06][^R07][^R08]

### 18.2 指标定义

| 指标 | 正确口径 | 避免的假好结果 |
|---|---|---|
| 转录保留率 | 已产生并被调用方接收的合法final中，成功存入正确会议的比例；另报上游未出final/采集丢失 | 只统计数据库里已经存在的行 |
| 尾句保存成功 | 满足完成屏障的尾部final进入正确源快照，含失败/超时次数 | transport ACK到达即算存完 |
| 来源处理覆盖 | 所有eligible source units被owned窗口覆盖并有明确处理结果；另外报告音频/转录本身缺口 | 所有窗口都跑了就声称实际会议内容无遗漏 |
| 决策/行动事实精确率 | 人工核对的生成条目中，内容、类型、条件、负责人、期限得到来源支持的比例 | 模型把所有字段写未知以抬精确率，却不报召回 |
| 关键内容召回率 | 参考标注的重要决定、行动、分歧被完整保留的比例 | 只看生成文本是否流畅或摘要与参考词重合 |
| 引用结构有效率 | 引用属于正确文档/快照/revision，范围存在且quote匹配 | 只要链接能点开就算证据正确 |
| 引用支持率/充分率 | 人工核对“该引文是否支持该条目”“是否遗漏必要限定或相反证据” | 引用确实存在但支持的是另一个结论 |
| 词法/语义检索 | Recall@K、MRR/nDCG按查询类别，另报精确专名与短中文词 | 仅测几个刚写入的新文档，不测旧版本/同名/删除 |
| 问答事实与拒答 | 有证据回答的支持率；无证据集的正确拒答；冲突集的正确展示 | 只测可回答题，或把没有结果排出样本 |
| 行动一致性 | 再生成、改名、移项目后稳定ID和执行状态保留 | 用“重新创建相似任务”替代更新 |
| 恢复完整性 | 新环境恢复后文档、版本、引用、行动事件、私密边界可核验 | backup命令exit0就算恢复通过 |
| 控制/隐私安全 | 旧事件/旧job/被删材料对新场或答案的未授权影响次数 | 只统计未抛异常，不检查错误对象写入 |

### 18.3 候选验收门槛，不是现有成绩

机械不变量应在确定性测试中全部满足：重复final不重复保存、错误文档ID/旧fence不提交、错误引用不升级、完整删除内容不复活、备份恢复失败不改原库。安全测试集出现一次跨会议写入或未授权泄露，都阻塞发布。

模型质量可先讨论下列候选目标：关键事实条目精确率不低于95%，重要决定/行动召回不低于90%，引用结构有效率100%，抽样引用支持率不低于95%。涉及错误负责人、金额单位、否定条件或把建议写成已决的高影响错误，单独逐例审查，不被总体平均值冲淡。

这些数字需要以用户认可的参考标注、足够样本及置信区间校准；观察到零错误不代表总体错误率为零。对未核对材料不得展示“已达95%可靠”这类个人结论。

性能建议先在1,000场会议/约100,000来源段的合成非隐私库建立词法基线，再按实际使用量扩展。可把暖缓存关键词检索P95≤300ms、正文打开P95≤300ms作为初始讨论目标；冷启动、索引重建、生成时间另行报告。FULL写入策略必须在实际设备上测量，不能为追求该数值牺牲持久化。

端到端纪要生成时间按输入长度、模型位置和窗口数分层；不承诺所有会议固定几秒生成。指标拆成排队、模型首响应、各窗处理、合并、校验、保存；失败任务与取消任务有独立统计，不从延迟图里悄悄删除。

### 18.4 数据保留与恢复目标

正常App崩溃的恢复目标至少覆盖最后一次明确保存回执之前的业务内容。系统崩溃/断电、磁盘损坏和误删属于不同故障模型，分别依赖提交策略、存储环境和备份；不能用一次进程kill证明所有故障下零损失。

备份频率及目标位置由用户设置；展示最近成功备份时点和可恢复范围。RPO是可能损失多长时间的数据，RTO是恢复所需时间，必须附对应数据体量/存储设备/操作步骤，未实测时填“未测”，不要填0。

### 18.5 观测的隐私边界

允许记录有界计数、持续时间、错误枚举、输入/输出规模、已处理窗口数、索引版本、匿名任务关联。禁止完整transcript/prompt/quote、PCM、Base64、真实姓名、用户路径、密钥或文档全文进入诊断日志。

UI“查看来源”属于业务读取，不等于诊断日志可以记录来源。测试报告仅存聚合值与虚构case ID；需要人工复核的真实样本放在用户控制的仓库外，并明确使用与保留范围。

### 19.3 数据迁移发布

迁移之前固定当前库schema、对象数量和选定样例，创建并验证备份。迁移在事务中完成，先增加结构和关联再切换读取；不破坏旧Markdown或删除旧问答。现有用户数据不是可为了current-only接口政策随意丢弃的兼容包袱。

老版本不认识新版schema时应安全拒绝写入；需要应用回退时使用独立的导出/恢复策略保留迁移之后的新内容，不能简单把可执行文件换回去让它重建库。来源缺失的历史纪要迁移为可读legacy文档；只有在用户明确生成新候选时才请求模型补充结构，不自动将所有老内容发往远端。

### 19.4 功能灰度与失败回退

新知识库读取可先对已迁移数据启用，索引延后构建；用户始终可从直接文档入口阅读已保存内容。生成pipeline、引用问答、语义召回应可分别停用，不能一个组件异常把整个历史库关掉。

回退优先停止新任务/切回旧呈现，不撤销用户采用或编辑。索引回退仅丢弃派生generation；知识数据回退必须显式导出并保留新写入。任何远端任务的取消状态单独报告，不能以本地开关关闭就声称云端请求已停止。

## 20. 风险、取舍与完成定义

### 20.1 主要风险与应对

| 风险 | 应对 | 不采用的捷径 |
|---|---|---|
| ASR误听进入长期知识 | 原始来源保留、校订revision、关键事实人工核对、缺口可见 | 认为summary模型会自动纠正所有误听 |
| 产品变成复杂知识管理系统 | 第一版只做会议文档、项目、来源、搜索；结构化事件按价值渐进 | 一开始部署图数据库、多Agent或通用实体本体 |
| 用户不愿逐项确认 | 自动保存可用稿，少量高风险事项集中提示，整体采用可选 | 没核对就不保存/不入库 |
| 模型成本和本机资源争抢 | 会议采集优先，任务预算有界，语义索引按需构建 | 开更多重模型进程提高吞吐 |
| 引用形式掩盖语义错误 | 分开评估引用存在与是否支持结论，保留上下文与反对意见 | 验证ID有效就显示“事实核实通过” |
| 修改来源导致大量过期内容 | 显式依赖关系，旧版本仍可读，按受影响范围重新核对 | 背景自动重生成并覆盖用户采用版 |
| 删除与审计互相矛盾 | 业务版本不可变但用户删除可执行；完整清理与外部副本告知 | 以审计为由暗中保留用户要求删除的全文 |
| 单机持久被误解为永久不丢 | 独立备份、恢复演练、开放格式与清晰故障模型 | 声称SQLite或FULL可以抵御所有损坏 |

### 20.2 本轮明确不做

不自动接入日历/邮箱/组织联系人，不替用户安排或发送后续行动，不默认下载embedding模型、不迁移到外部向量服务、不保留原始会议PCM、不识别真实说话人跨会议身份，不启用公共云同步或多用户共享，不执行本方案的测试和部署。

用户将来批准扩展时，再为相应连接器、导入权限、组织保留策略和多人访问控制增加范围；不让这些远期问题阻塞当前可用的持久知识库。

### 20.3 完成定义

满足下列场景，才可以说会议助手具备“持久知识库”，而不是“生成过几份纪要”：

用户结束一场会议，关闭App，再离线打开时，仍能找到该场文字与已存纪要；重新生成失败，采用版不变；修改一条结论，原文和旧版仍可回查；两个月后搜索一个项目决定，能够看到当时的依据及后来的明确修订；停用语义模型或重建索引不丢资料；导出并恢复到临时新库，来源与版本关联仍可核验；用户完整删除后，搜索、问答和旧后台任务不再把它带回来。

**推荐先交付可靠保存和证据化纪要，再交付知识组织与跨会议复用；任何“智能增强”都不得削弱上述底线。**
