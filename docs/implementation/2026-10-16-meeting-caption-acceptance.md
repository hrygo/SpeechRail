与 [D0–D6](../superpowers/plans/2026-10-16-meeting-diarization-implementation.md)。
核验日期为 2026-10-16，时间为 Asia/Shanghai。代码实施、真实模型回放、真实采集 UI、
长时稳定性和生产启用是不同结论；当前不能宣称全部验收通过。

## 缺陷修复与诊断

- 保留此前滚动跟随与几何反馈环修复；静止页面观察期间没有重现 App 单核持续占满。
  此结论不覆盖尚未完成的活动采集长时压力。
- 对齐 adapter 不再把真实的零宽度词时间伪造成精确词边界。句段级输出合并坍缩时间；
  词级裁剪报告 `alignment_time_resolution_insufficient`，最多做一次 owned-only 回退。
  原始模型时间分辨率与所需逐词边界不足，不能用插值时间掩盖。
- 真实日志诊断提取到 181 次分辨率失败、660 个坍缩 token；一个 14 秒、37 token 的样例
  有 3 个零宽度 token，实际时间网格约 80 ms。这里只记录计数与原因，不复制原文。
- 安装态字幕回放曾暴露同一 window revision 被 sealed 与后续 updated 复用。
  现在在事件首次 await 前预留 wire revision；独立审计器的失败证据保留，确定性反例通过。
- 关闭单元的预览失败只允许 500 ms 后再试一次；永久失败不忙轮询。
  账本拒绝封存后改字、同 revision 不同正文及终态 CAS 冲突。
- 采集启动等待上限 45 秒；同步 CoreAudio 清理上限 8 秒。
  不可取消的 HAL 调用由隔离 helper 的 watchdog 退出回收，App 不再无限停在准备页面。
  原始 OSStatus、有限阶段与 NSError domain 被保留，避免只显示 Swift 枚举的 `error 2`。
- helper 按连接绑定上行代理与硬件 owner。旧失效回调不能停止新 owner；
  有效连接仍持有采集时拒绝其他连接抢占，避免来源自动重连互抢。
- 字幕浮层内容增长曾被当作用户向上滚动，提前关闭末行跟随；窗口回溯文字与同一行的修正
  也未触发滚动。浮层采用共享的用户滚动意图策略，使用原生底边尺寸锚定；
  显示、高度计算和滚动变化检测共用可见文字投影，协议空修订不产生滚动请求。
- 静音确认事务没有文字，仍必须推进保存屏障；它曾反复显示为“文字已确认，正在保存”，
  造成“已保存”闪烁。状态仅在真实文字变更待保存时切换，未变化的预览与空检查点不重复写入；
  删除旧尾文、保存错误、容量拒绝及结束确认仍保留原有的恢复与屏障语义。
- 协议排空或数据库归档失败时，空保存队列曾继续显示“已保存”，关闭浮层后主页也不显示
  收尾错误。状态改为“字幕收尾尚未确认”，主页保留原因，并可查看失败阶段；
  两种失败分别注入回归。帮助文案同时明确：⌘⇧L 暂停/继续，浮层 ✕ 结束并保存。
- 收尾回执未裁剪重采样补齐尾帧：24 kHz 输入转为 16 kHz 后，部分输入长度在映回 wire
  时间轴时会多 1 个采样。窗口事件已经裁到输入末端，回执却没有，触发客户端严格拒绝。
  确定性反例为 512 → 513、16,001 → 16,002；旧安装态 API 也复现接收/窗口封存 24,512、
  回执封存 24,513。回执现在按本次冻结输入上限裁剪，保留全部原始输入和严格校验。
  客户端另记录稳定错误码与数值水位，不记录音频、正文或模型路径；主页诊断保留错误码。

## 公开语料与真实模型

AISHELL-4 固定通道的 12 场自然会议共 125.624 分钟，每场约 6–7 个局部说话人编号；
开发集 8 场约 82.314 分钟，锁定留出集 4 场约 43.310 分钟。
使用 [AISHELL-4 官方](https://www.openslr.org/111/) CC-BY-SA-4.0 许可；
源 manifest 保留固定 revision 与逐文件 SHA-256。
人工原始标注不变，ASR 派生参考仅过滤明确的非词汇事件标记。
局部编号不能证明跨场参与人身份，不能据此认证“10 个独立人”或人互斥留出集。

另取得 AMI 官方人工标注 1.6.2 与 3 场混合音频，共 57.696 分钟、12 个全局匿名参与者。
按[官方许可与下载说明](https://groups.inf.ed.ac.uk/ami/download/)使用 CC-BY-4.0。
AMI 词时间是[自动强制对齐结果](https://groups.inf.ed.ac.uk/ami/corpus/transcription.shtml)，
不能用作独立人工词时间真值；
尚未把这 3 场作为已完成模型质量验收。

### 字幕窗口探索回放

以下均为同一个 602.704375 秒开发片段的公共 API 回放，不能当作场景配对质量结论：

| 实验 | 规范化 CER | 失败窗口 | 结论 |
|---|---:|---:|---|
| 原安装路径 | 377/2300 = 16.3913% | 不适用窗口审计 | 1000 ms 预览、20 s 旧策略 |
| 早期窗口候选 | 492/2300 = 21.3913% | 6 | 保留失败，不启用 |
| 安装态候选 6 | 393/2300 = 17.0870% | 0 | 全部 14,464,905 wire samples 覆盖完整，无终态冲突 |

候选 6 有 149 个窗口事务、1195 次预览；首个预览收到时间约为回放开始后 0.498 秒，
commit 后收到终态约 0.783 秒。这是客户端收包时间，不是声学词尾到 UI 显示时间。
该轮有 143 次对齐分辨率回退及 5 次词跨 owned 边界回退；它们说明上下文裁剪退化的频率，
不能单独证明 CER 损失的全部原因。

收尾边界修复后的安装态回放另验证两组输入：24,512 个合成静音采样的接收量、
窗口封存与回执均为 24,512，独立审计通过；20 秒公开音频加 2 秒静音和 2 个尾采样，
共 528,002 个采样，产生 6 条非空转写，窗口与回执封存一致、零失败窗口、无序列异常，
分人结束屏障及 clear 发送完成。这里验证协议和收尾功能，不重复用该 smoke 宣称准确率。

基线与候选的预览节奏、切分策略和冷热状态未形成完整配对矩阵；只有一个独立会议，
不能生成可信的跨会议置信区间。当前没有窗口质量收益的证据，因此不默认启用。

### 多人动态分人开发门

锁定 SDK、模型 snapshot 与原生 binary；在 8 场开发会议上比较 24 组匹配策略。
没有一组同时满足已冻结的准确率/覆盖率门。最佳候选的整场 known accuracy
约为 88.76%–97.34%；即使使用仅供诊断的 oracle 身份合并，仍有 5/8 场低于 95%。
因此问题包含声学局部聚类与活动覆盖损失，不能只靠跨窗 ID 合并解决。
未知区间、短插话和失败输入没有从分母删除；holdout 未用于反复调参。

结论为 `production_certified=false`、无 winner。没有伪造 policy 认证摘要，
没有将 32 身份容量当作质量认证，也没有静默用四槽输出来宣称支持更多参与者。

## 实机 UI 与资源证据

静止会议页超过 5 分钟，App 未观察到 CPU 空转；静止字幕页超过 5 分钟，
App 区间 CPU 平均约 2.59%、p95 约 17.46%、峰值约 29.95%。
正常 ASR worker 的计算负载不适用 App 静止页面的空转门。

公开音频通过 QuickTime Player 播放，App 仅选择该来源，麦克风关闭。
授权刷新前的两次会议启动均未取得 PCM，也未创建新会议记录：

1. 首次 `AudioDeviceStart` 长时间阻塞，返回 OSStatus 268451843 后，
   `AudioDeviceDestroyIOProcID` 清理继续阻塞；原始错误被同步清理与通用 NSError 桥接掩盖。
2. 增加 deadline/watchdog 后，第二次样本停在 `AudioDeviceCreateIOProcID` 的 HAL 服务等待。
   App 在约 45 秒后回到“这一场没有开始”并显示超时提示，没有无限等待。

第二次请求的 TCC 日志确认 `kTCCServiceAudioCapture` 代码签名匹配失败，
preflight `authValue=1`；系统设置中的既有“仅系统录音”仍显示开启。
这构成授权失效的具体线索。用户完成 macOS 触控 ID/密码验证后，系统设置中的既有
“仅系统录音”已开启；未修改权限数据库，
未重启 coreaudiod，未扩大到录屏权限。

授权刷新后的实测：

- 标准会议路径取得 PCM、产生正文并成功归档。
- 窗口会议约 6 分 5 秒，暂停/恢复后继续出字，结束排空后保存 27 行、4 个会话内匿名标签。
  音频原始音量较低，期间改用响度归一化的公开副本，仅验证采集与交互，不用于准确率评分。
- 首轮窗口字幕约 14 分 50 秒，保存 14 行并成功归档。用户确认浮层可见、文字持续更新，
  同时报告末行跟随失效与静音保存提示闪烁，因此该轮不能作为字幕展示通过的证据。
  浮层修复版完成本机构建和替换后，用户明确确认“末行跟随正常，回看也正常”，
  并在最后一句保存后观察静音阶段，确认“已稳定，不再闪烁”。
- 浮层复测的一条 7 行记录曾出现 UI 已空闲但数据库仍为 `recording`、`ended_at=NULL`。
  正文已落库，但不能据此声称正常结束成功；只读备份保留后，App 再次启动按既有规则
  将其标记为 `unexpected_exit`。该恢复结果不证明原收尾根因已修复。
  因旧 UI 没有保留可见原因，本次补齐诊断后另做真实采集复核。
- 中间诊断版的短复测正常归档 13 行；随后播放约 65 秒、静音约 189 秒的复测再次出现
  收尾拒绝，40 行正文保留，主页明确显示错误。通用“事件顺序或身份无效”提示并不等于
  已证实序列缺口；进一步 API 反例确认上面的回执边界不一致，并补充精确错误码与水位日志。
  该 40 行失败记录在再次启动时按 `unexpected_exit` 恢复，未改写成正常结束。
- 最后 App 与回执修复服务的字幕复测持续 300.23 秒，播放公开音频约 74 秒后静音超过
  3 分钟；结束后记录为 `archived`、`end_reason=user`，24 行、零残留半句，WebSocket
  释放，观察区间无协议拒绝日志。该轮说话人辅助结果为 `degraded`，不宣称归属全部完成。
  浮层滚动和静音提示的用户确认来自前述同一 UI 实现；此轮额外验证实际结束与归档。
- 最后 App 的会议复测仅选 QuickTime Player、关闭麦克风，65.49 秒内取得系统音频并
  保存 6 段文字；结束后 `archived`、`end_reason=user`、零残留半句。界面显示 1 个匿名
  标签，数据库辅助分人状态仍为 `active`；这是采集和正常归档 smoke，不是多人质量验收。
- 会议活动采样区间内 App CPU 峰值约 48.38%；首轮字幕 319 个约 2 秒采样区间内，
  App CPU 平均 23.96%、p95 30.02%、峰值 33.91%，未见单核持续占满。
  第一份连续采样因进程发现超时中断，之后续采；这些是有范围和间隙的观察，不能充当完整压力门。
- 浮层修复版公开音频阶段 53 个采样区间，App CPU 平均 19.22%、p95 28.42%、峰值 28.93%；
  静音阶段 66 个采样区间，平均 9.07%、p95 25.70%、峰值 32.42%。输入与时段未配对，
  这些数值不能用于宣称性能提升比例。

计划的 30–60 分钟活动压力仍未完成；准备、暂停及无输入等待不计为持续活动压力。
字幕正确改错率、事实准确率、词表负对照与声学词尾到 UI 的延迟仍为 not_observed，
没有用模型输出或自动对齐充当人工真值。

App 的窗口投影保留 `lastUICommitAt` 本地时钟。
回溯评分工具仍要求人工 token 对应与人工音频词时间；其输入时钟声明保持 unverified，
不自动签发生产启用结论。详见[准备和验收手册](../operations/meeting-caption-recognition.md)。
